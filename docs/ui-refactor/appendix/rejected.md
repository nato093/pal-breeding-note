**理由**（判断）

理想個体の画面はすでに条件の欄と説明（views/ideal.js:155-170 の 15 項目の説明）が重い。チップを押すと「必ず⇄あれば」が切り替わる隠れた操作、URL の o、cleanGoal の互換、「タマゴの平均が 1 割以内の組どうしは期待数で並べ替える」という分かりにくい規則を足すと、かえって複雑になる。passiveChance と完全体の表は欲しいパッシブの数をもとに組まれていて（core/ideal.js:694-760）、「あれば」の期待数を足すと性能テスト（1 回 2 秒）の計り直しが要る。今でも欲しいパッシブを 1 つ外せば同じ比較ができ、外したときの結果は URL ですぐ切り替えられる。妥協の計画が欲しい場面は、X-22 の修正版（手術で付ける分を除いて計画するリンク）の方が簡単にまかなえる。INV-2 の違反はない。

**もう一方の判定**（事実確認・そのまま）

現状は正しい。欲しいパッシブは MAX_WANTED で最大 4 個に切っていて（views/ideal.js:179）、すべて必須。passiveChance（core/ideal.js:54-76）は、全部を継ぐ確率だけを出す。2 段に分ける仕組みは、コードにも説明にもない。性能テストは 2 秒以内を確かめている（test/perf/ideal.perf.js:24・48 で idealPlan も測っている）。cleanGoal（core/ideal-goals.js:41-）に optional はないので、互換に気をつける必要がある（リスクに書いてあるとおり）。補足として、「配合では作れません」の文（views/ideal.js:391）が出るのは、候補のだれも持たないパッシブがあるときで、4 個を選んだこと自体で出るわけではない。

**提案**（却下した案の原文）

1. 欲しいパッシブのチップを押すと「必ず ⇄ あれば」が切り替わるようにする。「あれば」は点線の枠で見分ける。URL は p（必ず）と o（あれば）に分ける。
2. 確率と並び順は今と同じく「必ず」だけで計算する。タマゴの平均が 1 割以内の組どうしは「あれば」の期待数で並べ替える。期待数は「必ず」を全部継いだうえで「あれば」が平均何個付くかで、passiveChance と同じ組み合わせの数え方で出せる。組のカードには「あれば: 神速 32%」と小さく添える。
3. 理想個体の登録と完成の判定（goalMatches）は「必ず」だけで行う。「あれば」も満たした完成品には「＋神速」の印を付ける。
4. 「あれば」は 2 個までにして計算の量を抑える（性能テストの 2 秒以内に収める）。
release-notes に足す。
