# 理想個体: 両親合わせてパッシブがそろう組も「完全体作成組」で計算し、交換推奨・「変更あり」は全体で早くなるときだけ出す

## Context

- ユーザーの指摘（画像）: 拠点 4 の牧場に ゴウカブキ（KabukiMan）♂A（欲しい 4 つちょうど・HP97/攻99/防96）×♀B（欲しい 4 つちょうど・HP97/攻99/防96）を置いている。
  ♀D（冷静沈着だけ・HP100/攻14/防96）がいるのに、♀B → ♀D の交換推奨が出ない。
- ユーザーの決定:
  - A「交換推奨は、完成までのタマゴの平均が今より少なくなるときだけ」＝はい
  - B「変更あり も同じ考え方」＝はい
  - 牧場が複数のとき＝「**最終的な理想個体ができるまでの速さで決める**。2 つ目以降の牧場の確率が下がっても、1 つ目の牧場で上がり、全体として早くなるならその選択をする」
  - 全体の速さは、各牧場の「1÷完成までの平均」の合計の**目安でよい**（厳密な計算はしない）
  - 牧場の数 K は、今までどおり「この目標の組が入っている牧場の数」。何か所に置くかはユーザーが決める（増やしたときの効果を出す機能は、今回は入れない）
- 手元・Codex・調査用エージェントの 3 者で、原因と数値が一致した（下記）。
- Codex のプランレビューは 3 回行い、指摘はすべて反映した（1 回目: 複数牧場の悪化・同点・境目・テスト。2 回目: R は目安・まとまりの頂点・watch の形・画面テスト・説明。3 回目: R＞0 の同点・欠損のまとまり単位・説明）。

## 原因（3 者一致）

1. 子を入れ替えながら作る世代の計算が、「両親**それぞれ**が欲しいパッシブを全部持つ」組に限られている（`web/js/core/ideal.js:718` の `ready`、`:816`）。
2. A×D はどの入り口にも入らず、個体値厳選組（rank 2）になる。
   - 世代の計算: ♀D が `ready` でない。
   - 1 回で作れる組（`:814` の `oneShot`）: 攻・防に 100 の親がいない。
   - パッシブ厳選組（`:826`）: A が 1 体で 4 つ全部を持つので、集まる数が増えない。
   ♂A が 1 番の A×B に使われるので、A×D は一覧に出ない。`farmAdvice` は A×B を「そのまま」と判定する。
3. 実際は A×D の方が早い。和集合は欲しい 4 つちょうどで、10% は A×B と同じ。そのうえ HP100 がある。
   - 同じ交換方針で、A×D は平均 **3,591.5 個**、A×B は **4,868.2 個**（約 26% 少ない）。
   - Codex は、D が未完成の間を別の状態として解いても同じ値になることを確かめた。
4. 世代の表の状態は「届くビット・余計の数・共有数」だけでできている。どの親が欲しいものを持つかは確率に効かない（ゲームの処理で確認）。
   入れ替えに使うのが「欲しいものを全部持つ子」だけなら、和集合がそろう状態は保たれるので、状態を足さずに使える（Codex レビューでも確認）。
   ただし今は、余計の数の上限が「4 − 欲しい数」になっている。

## ゲームファイルでの確認（v1.0.5 build 25246127。調査用エージェントは dumpbin で逆アセンブルし直し、前回の .asm と差分 0 行。Codex も別に確認）

- パッシブ（RVA 0x2E8F8A0）
  - 親 A のリストに、親 B のうち入っていないものを足した**和集合**から、取り除きながら同じ確率で選ぶ。**どちらの親かは見ない**。
  - 継ぐ数は [4,3,2,1]。余計なパッシブが 1 つ増えるごとに、そろう確率が下がる（欲しい 4 つ: 10% → 2%）。
- ランダムに足すパッシブ（0x3150BE0）
  - 候補は AddPal の 85 件（重み付き）で、継いだものは除く。不死身（突然変異専用）・伝説・世界樹は入らない。
  - 欲しいもの・親の余計なものが偶然付くことはわずかにある（4 つそろう確率は 10% → 約 10.05%）。今の計算は下限のまま変えない。
- 個体値（0x2E909B0）
  - `TALENT_PATTERNS` と完全に一致する（HP 2/3・攻防 5/9。どちらの親かは 50/50）。
  - 乱数は 0〜100 で、ほぼ均等（実際は 325/32768）。
  - キノコ・豪華野菜ケーキの +1〜5 は、写した値にも乱数にもかかり、100 で頭打ち。スペシャルケーキは PassiveInheritCountOverride = 4。
- 子の性別（0x2E89200）
  - 種族ごとの MaleProbability で決まり、親の性別は見ない。今の計算は半々と置いている。
  - → **今回は扱わない**（`docs/ui-refactor/appendix/catalog.md:12212` に「要ユーザー判断」の案として載っている）。

## 方針

### 1. 完全体作成組を「同じ種族で、両親合わせて欲しいパッシブがそろう組」に広げる（`web/js/core/ideal.js`）
- `idealPlan`: 世代の計算の条件を、`male.ready && female.ready` から「同じ種族・`union === full`・各親のパッシブ 4 個以下」に変える。
  - `complete.M/F`・`tooMany` の数え方（画面の「5 個以上は除外」の注記）は、今の意味のまま残す。
  - 異なる種族の `oneShot` は、今のまま残す。
- 余計の上限: `generationTable` に `parentExtras` を足す。
  - `parentExtras` は整数で、範囲は「4 − 欲しい数」〜 4。
  - ただし、パッシブを見ない表（`ignorePassives`: 欲しい 0 個・含む）では、実効の上限を 0 のまま保つ（個体値厳選組の表を 64 → 8,000 状態に膨らませないため）。
  - 実効の値に正規化してから、`GENERATION_TABLES` のキーに入れる。
  - `buildGenerationTable` の `span`・`valid` のループ・`indexOf` はこの上限を使う。子の余計の上限（`limit` = 4 − 欲しい数）は変えない。
  - `value()` に範囲の検査を足し、範囲外は Infinity を返す。今は範囲外の引数が、黙って別の状態の値を返す。
    検査するのは、整数であること、ビットが 0〜7、負でないこと、上限以下であること、shared ≤ min(em, ef)。
- `idealPlan` は、表を作る前に、同じ種族の ♂・♀ の「欲しいパッシブの mask」の組み合わせを見る（mask は高々 16 通り）。
  - 和集合がそろう相手がいる親だけから、余計の最大を求めて `parentExtras` にする（無駄に表を広げない）。
  - そういう組が 1 つもなければ、表を作らない（`complete.M && complete.F` の判定を置き換える）。
  - `entry.stage` は表ができてから求める。
- 結果として、同じ種族で和集合がそろう組は、パッシブ厳選組（rank 1）ではなく完全体作成組（rank 0）になる。
  パッシブ厳選組に残るのは、和集合でまだそろわない組と、異なる種族で 1 回では作れない組。
- `idealPairs`（画面では使っておらず、テストだけが使う）は変えない。

### 2. 並びの同点を安定させる（`comparePlan`）
- 主な物差しを、丸めた比較キー（`Number(x.toPrecision(12))`、Infinity はそのまま）で比べる。対称な条件でも、末尾の誤差で同点が崩れないようにするため（Codex の指摘）。
  - 主な物差しは、完全体作成組 `eggs`、パッシブ厳選組 `gathered`・`gatherChance`、個体値厳選組 `talentEggs`。
- 並びは「主な物差し → 優先 → 残り」の順にする。
  - 優先: 今の牧場の組 2 ／ 前の基準の上から K 組 1 ／ それ以外 0
  - 残り: `chance` または `talentChance` → `expected` → `extraCount` → 個体 ID
- `idealPlan` に任意の `prefer: { placed: Set<key>, baseline: Set<key> }` を足す。キーは `planPairKey`。
  固定の優先を辞書式の比較に足すだけなので、全順序と `2×limit` の枝刈りの証明はそのまま成り立つ（Codex 確認済み）。

### 3. 交換推奨を「全体で完成が早くなるときだけ」にする（`web/js/core/ideal-farms.js` の `farmAdvice`）
- 今の割り当て（上から K 組を、親の片方が同じ牧場を先にして置く）で、案を作るところまでは変えない。
- 案の交換を「個体をやり取りする牧場のまとまり」に分ける。
  - 対象の牧場（`none` を含む）を頂点とし、新しい組の個体の移動元と移動先を、無向・推移的につなぐ。これで、却下して戻した個体が別のまとまりで使われることは起きない（Codex 確認）。
  - パルボックスの個体と、ほかの目標の牧場（`targetFarms` の対象外）の個体には、移動元の頂点がない。この目標の速さだけで比べる（今と同じく「入れる」欄に場所を出す）。
  - `keep` の牧場の親は、おすすめが個体を重ねて使わないので、ほかへ貸し出されない。
- まとまりごとに、今と案を比べる。良くなるときだけ交換を勧め、良くならなければ、そのまとまりの牧場を全部「そのまま」にして `to`・`in`・`out` を消す。
  1. **完成の速さの目安** R = Σ 牧場ごとの rate。
     - rate は、完全体作成組なら 1 ÷ 完成までの平均。それ以外の組は、1 個のタマゴで完成する確率 `chance`（親を替えないときの速さ。異種で乱数しだいで作れる組も入る）。
     - 相手がいなくなる牧場は 0。`none` で `out` が空なら、今の組がそのまま残る。
     - R が増えれば交換、減れば「そのまま」。丸めたキーで比べる。
  2. **今も案も R = 0 のときだけ**（どの牧場も完成できない、準備の組だけのとき）、どの牧場も「rank → rank ごとの丸めた主な物差し」で悪くならず、1 か所以上が良くなるときだけ交換。準備段階の補助の判定として、画面の説明にも書く。
     R が同じで 0 より大きいときは「そのまま」（完成の速さが同じなので。Codex の 3 回目の指摘: 異種のパッシブ厳選組で chance が同じなのに gatherChance だけ上がる例）。
  - 例（Codex の反例 1）: 359.2・359.2 → 357.1・486.8 は R が下がるので勧めない。
  - 牧場が 1 か所のときは、R は正確（1 ÷ 平均）なので、「その牧場の平均が減るときだけ」と同じになる（A）。
- **R は目安**（各牧場が一定の確率で完成するとみなした値）。Codex は、R がわずかに上がっても最初の完成までの平均が 209.850 → 209.898（約 0.02%）悪くなる反例を出した。
  厳密な E[min(T₁, T₂, …)] は、状態の分布を何千個ものタマゴにわたって追う必要があり重いので、採らない。画面とプランでは「全体の速さの目安が上がるとき」と書き、「必ず早くなる」とは書かない。
- 今の牧場の組の物差しは、一覧に入っていないこともある。なので `idealPlan` に `watch`（牧場の組のキーの集合）を渡し、`measures` を `pairs` とは別に返してもらう。
  - 形: `Map<key, { status: 'ok', rank, eggs, gathered, gatherChance, talentEggs, chance } | { status: 'blocked' }>`。watch の組を `pairs` に足さない。
  - 個体値厳選組で、枝刈りのために平均を求めない処理（`:833`）も、`watch` の組では必ず求める。
  - `impossible`・パッシブの条件を満たせない組は blocked として返す（rate 0・rank は最悪）。
  - layouts にない組・候補にいない組は、`targetFarms` がそもそも対象にしないので返らない（ふつうの画面の流れでは起きない）。
    返らない組を含むまとまりは、比べられないので、**まとまり全体を**今と同じ動き（案のとおり交換推奨を出す）にする。1 牧場だけ戻すと、まとまりの一括の判定が崩れるため。
- `farmAdvice(farms, pairs, { measureOf })` の形にする。`measureOf` がなければ今と同じ動き（遺伝の計算は持たず、受け取った数だけを比べる、という今の原則を保つ）。
- 「そのまま」の表示: 一覧に入っていない組、または上から K 組より下の組なら「そのまま（入れ替えても全体の速さの目安が上がりません）」にする。

### 4. 「変更あり」を交換推奨に揃える（B）
- `planChanges` と、保存している基準の形（`web/js/ideal-plan-memory.js`）は変えない。
- 画面では、`planChanges` の `changed` を「採用した交換推奨の行き先の組」との共通部分に絞ってから表示する（Codex 確認: core の意図を保ったまま、表示だけを絞れる）。
- 同点の入れ替わりは、2 の優先で起きない。

### 5. 画面の流れ（`web/js/views/ideal.js` の `renderResults`）
1. `breedingLayouts(state.index, to)` → `targetFarms` → `farmSignature`
2. `planMemory.get(id)` を 1 回だけ取る。署名が合うときだけ、上から K 組を `prefer.baseline` にする（合わなければ空）。
3. `idealPlan({ ..., prefer, watch })`
4. `farmAdvice(placedFarms, result.pairs, { measureOf })`
5. `planChanges`（同じ基準と署名を渡す。reset なら、計算の後に保存する）→ 4 で絞る

  - Codex の簡易計測（テストランナー外）では、今のコードでも 1M 組が約 3.25 秒だった。実装前に、手元で今の値を `npm run test:perf` で測り、同じ条件で比べる。
- 画面: `npm run dev` で理想個体タブを開く。画像と同じ 4 体の条件で、1 番が ♂A×♀D、牧場が「交換推奨 → おすすめ 1 番（外す ♀B・入れる ♀D）」になることを確かめる。

## 前提・リスク

- R は「各牧場が一定の確率で完成する」とみなした目安。入れ替えながら作る過程や、牧場どうしで子を融通することは数えない。
  R が上がっても、ごくわずかに遅くなる場合がある（Codex の反例で約 0.02%）。牧場が 1 か所なら正確。
- 上から K 組を置く割り当て自体（貪欲法）は変えない。今の組を優先した選び方で、後の組が少し悪くなる場合がある（Codex の中程度の指摘）。全体が最適になる保証はない。
- 子の性別は半々、ランダムに足されるパッシブは新しいもの、という近似は変えない（ゲームより少し悲観的）。
- 基準（planMemory）の形は変えないので、保存済みのデータはそのまま使える。
