## ideal-calc: 両親合わせてパッシブがそろう組も完全体作成組にし、交換推奨と「変更あり」を全体の速さの目安で決める

### 目的

- 同じ種族で、**両親合わせて**欲しいパッシブがそろう組を、パッシブ厳選組ではなく完全体作成組（子を入れ替えながら作る世代の計算）にする。今は「両親**それぞれ**が欲しいパッシブを全部持つ」組だけが世代の計算に入る。
- 配合牧場の交換推奨を、**全体の速さの目安 R が上がるときだけ**出す（牧場が 1 か所なら「その牧場の完成までの平均が減るときだけ」と同じ）。同点（平均が同じで、個体値の期待値や個体 ID の差だけ）では「そのまま」。
- 「変更あり」を、採用した交換推奨の行き先の組だけに付ける（交換推奨と同じ考え方）。

- **原因**（手元・Codex・調査用エージェントの 3 者で、原因と数値が一致）:
  1. 子を入れ替えながら作る世代の計算が、「両親それぞれが欲しいパッシブを全部持つ」組に限られている（core/ideal.js:718 の `ready`、:816）。

- **候補の分け方**: `idealPlan`（core/ideal.js:694-878）は、目標の種族で欲しいパッシブを全部持ち、パッシブが 4 個以下の個体を `ready`（:718）にし、`complete.M/F` に数える（:719）。全部持つが 5 個以上なら `tooMany`（:720。画面の「5 個以上は除外」の注記）。

### 実装の手順

**1. 完全体作成組を「同じ種族で、両親合わせて欲しいパッシブがそろう組」に広げる**（core/ideal.js）

1. `idealPlan` の世代の計算の条件（:816）を、`male.ready && female.ready` から「**同じ種族・`union === full`・各親のパッシブ 4 個以下**」に変える。
   - `complete.M/F`・`tooMany` の数え方（画面の「5 個以上は除外」の注記）は、今の意味のまま残す。
   - 異なる種族の `oneShot`（:814）は今のまま残す。
2. 余計の上限: `generationTable` に `parentExtras` を足す。
   - `parentExtras` は整数で、範囲は「4 − 欲しい数」〜 4。
   - ただし、パッシブを見ない表（`ignorePassives`: 欲しい 0 個・`include`）では、実効の上限を 0 のまま保つ（個体値厳選組の表を 64 → 8,000 状態に膨らませないため）。
   - 実効の値に正規化してから、`GENERATION_TABLES` のキー（:452）に入れる。
   - `buildGenerationTable` の `span`・`valid` のループ（:369）・`indexOf`（:345）はこの上限を使う。**子の余計の上限（`limit` = 4 − 欲しい数）は変えない**（入れ替えに使う子は欲しいものを全部持つので、子の余計は 4 − 欲しい数を超えない）。
   - `value()`（:436）に範囲の検査を足し、範囲外は `Infinity` を返す。確かめるのは、整数であること・ビットが 0〜7・負でないこと・上限以下であること・`shared ≤ min(em, ef)`。
3. `idealPlan` は、表を作る前に、同じ種族の ♂・♀ の「欲しいパッシブの mask」の組み合わせを見る（mask は高々 16 通り）。
   - 和集合がそろう相手がいる親だけから、余計の最大を求めて `parentExtras` にする（無駄に表を広げない）。
   - そういう組が 1 つもなければ、表を作らない（:749 の `complete.M && complete.F` の判定を置き換える）。
   - `entry.stage` は表ができてから求める（:753-758）。
4. 結果として、同じ種族で和集合がそろう組は、パッシブ厳選組（rank 1）ではなく完全体作成組（rank 0）になる。パッシブ厳選組に残るのは、和集合でまだそろわない組と、異なる種族で 1 回では作れない組。

**2. 並びの同点を安定させる**（`comparePlan`）

1. 主な物差しを、丸めた比較キー（`Number(x.toPrecision(12))`。`Infinity` はそのまま）で比べる。対称な条件でも、末尾の誤差で同点が崩れないようにするため（Codex の指摘）。主な物差しは、完全体作成組 `eggs`、パッシブ厳選組 `gathered`・`gatherChance`、個体値厳選組 `talentEggs`。
2. 並びは「主な物差し → 優先 → 残り」の順にする。**rank → ambiguous は今のまま先に比べ**（:212-214）、同じ rank・ambiguous の中でこの順にする。
   - 優先: 今の牧場の組 2 ／ 前の基準の上から K 組 1 ／ それ以外 0。
   - 残り: `chance` または `talentChance` → `expected` → `extraCount` → 個体 ID。「`chance` または `talentChance`」は、個体値厳選組（rank 2）は `talentChance`、それ以外は `chance` と読む（原文はどちらを使うかを書いていない。今の rank 1 は `gatherChance` の後に `chance` を見ていないが、`chance` を足しても同点の分け方が増えるだけ）。
3. `idealPlan` に任意の `prefer: { placed: Set<key>, baseline: Set<key> }` を足す。キーは `planPairKey` と同じ形 `${male.id}|${female.id}`（core/ideal.js は ideal-farms.js を import できないので、中で作る）。固定の優先を辞書式の比較に足すだけなので、全順序と `2×limit` の枝刈りの証明はそのまま成り立つ（Codex 確認済み）。

**3. 交換推奨を「全体で完成が早くなるときだけ」にする**（core/ideal-farms.js の `farmAdvice`）

1. 今の割り当て（上から K 組を、親の片方が同じ牧場を先にして置く）で、案を作るところまでは変えない。
2. 案の交換を「個体をやり取りする牧場のまとまり」に分ける。
   - 対象の牧場（`none` を含む）を頂点とし、新しい組の個体の移動元と移動先を、無向・推移的につなぐ。これで、却下して戻した個体が別のまとまりで使われることは起きない（Codex 確認）。
   - パルボックスの個体と、ほかの目標の牧場（`targetFarms` の対象外）の個体には、移動元の頂点がない。この目標の速さだけで比べる（今と同じく「入れる」欄に場所を出す）。
   - `keep` の牧場の親は、おすすめが個体を重ねて使わないので、ほかへ貸し出されない。
3. まとまりごとに、今と案を比べる。良くなるときだけ交換を勧め、良くならなければ、そのまとまりの牧場を全部「そのまま」にして `to`・`in`・`out` を消す。
   - **見送った牧場の戻り値の形**（原文は形を書いていないので、この文書で決めた）: `status: 'keep'`、`rank` は今の組の計画での順位（一覧になければ -1。K 以上のこともある）、`to`・`in`・`out` なし。もとが `none` だった牧場も同じ。ふつうの keep は必ず `0 ≤ rank < K` なので、**画面は「keep で rank が -1 か K 以上」を見送りとして扱う**（手順 7 の文。今の views/ideal.js:418 は keep を「おすすめ rank+1 番」と出すので、rank が -1 だと「0 番」になってしまう）。
   1. **完成の速さの目安** R = Σ 牧場ごとの rate。
      - rate は、完全体作成組なら 1 ÷ 完成までの平均（`eggs`）。それ以外の組は、1 個のタマゴで完成する確率 `chance`（親を替えないときの速さ。異種で乱数しだいで作れる組も入る）。
      - 相手がいなくなる牧場は 0。`none` で `out` が空なら、今の組がそのまま残る。
      - R が増えれば交換、減れば「そのまま」。丸めたキーで比べる。
   2. **今も案も R = 0 のときだけ**（どの牧場も完成できない、準備の組だけのとき）、どの牧場も「rank → rank ごとの丸めた主な物差し」で悪くならず、1 か所以上が良くなるときだけ交換。準備段階の補助の判定として、画面の説明にも書く。
   3. R が同じで 0 より大きいときは「そのまま」（完成の速さが同じなので。Codex の 3 回目の指摘）。
   - 例（Codex の反例 1）: 359.2・359.2 → 357.1・486.8 は R が下がるので勧めない。
   - 牧場が 1 か所のときは R が正確（1 ÷ 平均）なので、「その牧場の平均が減るときだけ」と同じになる（決定 D9）。
4. **R は目安**（各牧場が一定の確率で完成するとみなした値）。R がわずかに上がっても、最初の完成までの平均が 209.850 → 209.898（約 0.02%）悪くなる反例がある（Codex）。画面とこのドキュメントでは「全体の速さの目安が上がるとき」と書き、「必ず早くなる」とは書かない。
5. 今の牧場の組の物差しは、一覧に入っていないこともある。そこで `idealPlan` に `watch`（牧場の組のキーの集合）を渡し、`measures` を `pairs` とは別に返してもらう。
   - 形: `Map<key, { status: 'ok', rank, eggs, gathered, gatherChance, talentEggs, chance } | { status: 'blocked' }>`。watch の組を `pairs` に足さない（一覧は変わらない）。
   - 個体値厳選組で、枝刈りのために平均を求めない処理（:833）も、`watch` の組では必ず求める。
   - `impossible`・パッシブの条件を満たせない組は blocked として返す（rate 0・rank は最悪）。
   - layouts にない組・候補にいない組は、`targetFarms` がそもそも対象にしないので返らない（ふつうの画面の流れでは起きない）。返らない組を含むまとまりは比べられないので、**まとまり全体を**今と同じ動き（案のとおり交換推奨を出す）にする。1 牧場だけ戻すと、まとまりの一括の判定が崩れるため。
6. 形は `farmAdvice(farms, pairs, { measureOf })`。`measureOf` がなければ今と同じ動き（遺伝の計算は持たず、受け取った数だけを比べる、という今の原則を保つ。core/ideal-farms.js:1-2 のコメント）。
7. 「そのまま」の表示: 今の組が一覧に入っていない、または上から K 組より下の組なら「そのまま（入れ替えても全体の速さの目安が上がりません）」にする（今の「そのまま（おすすめ N 番）」は、上から K 組に入っているときだけ）。見分け方は手順 3-3 の戻り値の形（keep で rank が -1 か K 以上）。

**4. 「変更あり」を交換推奨にそろえる**（決定 D10）

2. 画面では、`planChanges` の `changed` を「**採用した交換推奨の行き先の組**」との共通部分に絞ってから表示する（Codex 確認: core の意図を保ったまま、表示だけを絞れる）。

### 前提とリスク

原文の「前提・リスク」（appendix/ideal-calc-plan.md の末尾）と、2026-10-12 の文書の点検で分かったこと。

- **R は目安**: 「各牧場が一定の確率で完成する」とみなした値。入れ替えながら作る過程や、牧場どうしで子を融通することは数えない。R が上がっても、ごくわずかに遅くなる場合がある（Codex の反例で約 0.02%）。牧場が 1 か所なら正確。
- **割り当ては貪欲法のまま**: 上から K 組を置く割り当て自体は変えない。今の組を優先した選び方（手順 2 の `prefer`）で、後の組が少し悪くなる場合がある（Codex の中程度の指摘）。全体が最適になる保証はない。
- **近似は変えない**: 子の性別は半々、ランダムに足されるパッシブは新しいもの、という近似は変えない（ゲームより少し悲観的）。
- **基準の形は変えない**: `planMemory` の形を変えないので、保存済みのデータはそのまま使える。
- **「5 個以上は除外」の注記が少なめに出る**: `tooMany`（core/ideal.js:720）は、欲しいパッシブを全部持つ 5 個以上の個体だけを数える。ideal-calc の後は、欲しいものを一部だけ持つ 5 個以上の個体も世代の計算から外れるが、原文のとおり数え方は変えない（手順 1-1）ので、views/ideal.js:447 の注記には入らない（点検での推測。実装のときに確かめ、注記の数を変えるならユーザーに確かめる）。
- **世代の表の作成時間**（点検で、今のコードを別プロセスで 3 回ずつ測った値。記録用の計測ではない）: 欲しい 4 つ（span 1）4〜9ms、欲しい 2 つ（span 3）52〜64ms、欲しい 1 つ（span 4）175〜260ms、欲しい 0・「だけ」（span 5、8,000 状態）約 200ms。ideal-calc の後は、欲しい 4 つでも余計 3〜4 個の親がいると span 4〜5 になり、表 1 つで約 200ms かかる見込み（キノコケーキでは表が 2 つ）。表は 8 件までキャッシュされるので、時間がかかるのは条件を変えて初めて作るときだけ。
  - これを受けて、ユーザーが **D18** を決めた（2026-10-12。README の 3-1）: 分けて回せる計算は 1 区切り 50ms 以内のまま、分けられない表の作成は、新しい表が要るときの 1 回だけなら **300ms まで**許す（先に「計算中」を出す）。超えたら、まず表の作成も分けて回す（stable-render の手順 F-5。core/ideal.js の中だけで済む見込み）。Worker は最後の手段で、そのときだけ import の制限（test/import.test.js:43）と data/SOURCES.md を変える前にユーザーに確かめる（README の 3-7 の 13）。
  - ideal-calc では表の作り方は原文のとおりにし、作成時間を測って記録する。今のコードのまま入れるので、stable-render が入るまでは、今と同じく計画の計算全体が同期で回る（表の作成が 300ms を超える条件でも、このテーマの完了は妨げない）。
- **過去の通知は直さない**: 2026-10-10 の通知（web/js/release-notes.js の `2026-10-10-ideal-changed-farm`）は前の仕様の説明のまま残す（配った通知の履歴。cleanup-dead-code と同じ扱い）。新しい仕様は、このテーマの release-notes で知らせる。
