## 共通パスワードと ID

- 更新後、所有者が Apps Script エディタで `setup()` を再実行する。`設定`・`Users`・`Users_test` シートと保護されたヘッダーを追加する。既存の配合データと設定値は変えない。
- 本番の共通パスワードは `設定` シートの `項目` が `共通パスワード` の行の `値` に保存する。初回は旧 Script Property `PASSCODE` を移行し、旧プロパティを削除する。旧値がなければ自動生成する。値はログに出さない。
- 変更するときは、そのセルを直接書き換えて利用者に新しい共通パスワードを伝える。値の列は書式なしテキスト（`@`）を保つ。数字だけの値も文字として入力する。
- 照合は前後の空白を除いた完全一致で、大文字小文字・記号・日本語を区別する。設定が空、シートや行がない、テスト値が空、両者が同じ場合は全リクエストを拒否する。
- `Users` は本番の ID 一覧、`Users_test` はテストの ID 一覧。列は `userId` / `createdAt`。利用者は画面の新規登録から ID を追加する。ID は制御文字と前後の空白を除いた1〜20文字で、全角英数や大文字小文字が違っても同じ ID とみなす。
- ID の確認・削除は該当する Users シートで行う。削除した ID の端末は次のデータ取得時にログアウトする。配合レコードの登録者名や既存レコードは変わらない。
- 利用者は設定画面の「ID を変更」（ヘッダーの ID のメニューにもある。2026-10-14 の copy-dead-ends の前は「名前を変更」）で自分の ID を変えられる（API の `rename`）。Users の行と、配合レコードの登録者名（削除済みを含み、全角英数や大文字小文字の違いも同じ名前とみなす）、OwnedWorlds の `uploadedBy` を新しい名前にそろえる。`updatedAt` は変えない。
  - Log には同じ `recordId`（操作の opId）で開始の `rename` と完了の `renamed` の 2 行が残る。`rename` だけの行は途中で止まった変更で、利用者が設定画面の「ID の変更を再試行」を押すと続きから行う。過去の Log の行は書き換えない。
  - 旧名は予約しない（ほかの人が新規登録できる）。旧名のままの別の端末は、次のデータ取得時にログアウトする。大文字小文字・全角半角だけの変更なら、ログアウトせず新しい表記にそろう。
  - 共通パスワードだけで動くため、画面を通さなければ他人の名前も変えられる（既存の配合の更新と同じ水準）。
- パスワード変更後は次の API 通信で再ログインが必要になる。端末には成功時の ID とパスワードを保存する。設定画面のログアウトでパスワードとキャッシュを消去し、次回入力用の ID は残す。
- テスト用は従来どおり Script Properties の `TEST_PASSCODE` を使う（AI・開発者専用）。`.env.local` の `PAL_TEST_PASSCODE` に保存する（コミットしない）。必要な場合のみ `TEST_PASSCODE` を消して `setup()` を再実行すると作り直される。
- **サーバー専用の ID**（2026-10-19。server の決定 7）: 専用サーバーの PC の常駐（下の「専用サーバー（ServerSync）と常駐（server-agent）」）は、人の ID ではなくサーバー専用の ID「サーバー」でログインする（本番は `Users`、テストは `Users_test` の行）。作るのは、画面の新規登録（作った端末はすぐログアウトし、自分の ID でログインし直す）か、常駐の `--signup`（`run-agent.ps1 -Mode Signup`。先に応答の環境を確かめてから作る）。共有した人（`uploadedBy`）とプレイヤーの対応を書いた人（`updatedBy`）がこの ID になる。常駐が自動登録する配合で、親 2 体の預けた人が違う・分からない（対応が 1 人にまとまらない）ときの登録者も、この ID になる（画面が登録するときは、そのときログインしている人〔遊んでいるホスト〕になる所。このままにすると決めた〔server の決定 21〕。自分の配合の絞り込みに出ないので、登録した後に配合の編集の登録者で直す）。設定の「プレイヤーの対応」の選択肢にもこの ID が出るが、人のプレイヤーには選ばない（選ぶと、そのプレイヤーが預けた配合の登録者が「サーバー」になる）。だれもこの ID を「ID を変更」で変えない（変えると常駐の設定の ID と合わなくなり、常駐は 30 分ごとにログインに失敗し続ける。変えたときは常駐の `install.ps1` を新しい `-UserId` でやり直す）。
- **共通パスワードを変えたら、常駐を入れた PC ごとに `install.ps1` をやり直す**（同じ引数でよい。前の `config.json` の項目は残る。暗号化したパスワード `passcode.dpapi` を書き換える）。常駐が動いていれば、表示される手順（`stop.request` → タスクが Ready → `Start-ScheduledTask`）で動かし直す。やり直さないと、常駐は前のパスワードのまま 30 分ごとにログインに失敗し続け、サーバーの共有と自動登録が止まる（ログの `login-failed`）。

## 配合を探す

- 配合検索・逆引き・一覧は、2026-10-15 に 1 画面「配合を探す」（`#/search`。`web/js/views/search.js`）にまとめた（README の D1。find-merge）。引くのは登録済みの記録だけ（INV-2。`web/js/core/record-search.js`）。
- 条件はヘッダーの下に固定した帯で選ぶ: 1 段目 [親1] ＋ [親2] → [子] とキーワード、2 段目 登録者・並べ替えと、右端に件数。親 2 体ならその組、親 1 体ならその親を使う配合（親1 でも親2 でも）、子だけならその子の配合、親と子なら「その親と何を組めばその子か」。何も選ばなければ全件（既定は更新日の新しい順。D6）。
- キーワードは親・子の和名（ひらがな・カタカナはそろえる）・英名・図鑑番号・登録者・メモで、空白で区切るとすべてを含むもの。登録者は「すべて」・自分・ほかの登録者（件数の多い順。名前の変更の前の古い名前も）・登録者未指定で、12 人を超えると検索つきの選択になる。
- 並べ替えは 更新日の新しい順・親の図鑑番号順・親の五十音順・子の図鑑番号順・子の五十音順。親・子の並びは 1 件 1 回で、「No.1 モコロン · 3 件」の見出しの行の下に短い式（親の並びは「相手 → 子」、子の並びは「親 ＋ 親」）でまとめる（前の一覧の「1 件を親ごとに 2 行」はやめた）。親を 1 体だけ選んでいれば、その親の見出しにまとめる。
- URL: `p1`・`p2`・`c`（パル ID）、`by`（登録者の ID）、`noreg=1`（登録者未指定）、`sort`（既定の updated は書かない）、`q`（キーワード。入力では履歴を増やさない）。前の `#/reverse?c=X`・`#/list` は、履歴を増やさずに `#/search?c=X`・`#/search` に書き換える（ブックマーク・保存済みの通知の href も同じ。`web/js/router.js` の `canonicalHash`）。
- 件数の行は「N 件」。親 2 体で同じ組に結果が複数あれば「· 同じ組み合わせで結果が複数あります」、すべての記録に親の性別があって子ごとに向きが違えば「· 親の性別で子が変わります」。親を 1 体だけ選んで 6 件以上なら、子ごとの件数のチップ（押すと子で絞る・もう一度で外す）を出す。0 件のときは、選んだ親・子を入れた登録の入口（「この組み合わせを登録」など）か、登録者・キーワードのときは「条件をすべて解除」。
- 所持の重ね表示（2026-10-15。owned-overlay）: 所持パルのデータがあれば、カードの親の絵の下に親にできる個体の数「♂2 ♀1」（0 体なら薄い字の「未所持」、タマゴ・グローバルパルボックス・性別不明だけなら「タマゴ等だけ」。全文は title）、子の下に「所持 N」を出す（押すと所持パルをその種族で開く）。帯の 2 段目の「所持」の切り替え: 「両親を持つ組を上へ」（`ownedfirst=1`。今の所持で両親を別々の個体の ♂ と ♀ で組める記録を、並びの中で先に。記録に親の性別があればその向きだけ）・「今の所持で作れる」（`make=1`。組めて、子をまだ持っていない記録だけ）。集計は `web/js/core/owned.js` の `ownedCounts`・`canPairRecord` で、所持パルのデータが変わったときだけ数え直す。
- 登録の入口（2026-10-15。register-entry。D2）: ヘッダーの常設の「＋ 登録」はなくした。配合を探すの見出しの右に、今の条件に合う登録のボタンを 1 つ（全件表示は「＋ 配合を登録」、親 2 体で結果があれば「この組み合わせで別の結果を登録」、親 1 体は「この親で配合を登録」、子だけは「この子の配合を登録」。どれも今の親・子を初期値に。0 件のときは空の状態のボタンだけ）。パル詳細の「この子の配合を登録」は、そのパルが産まれる配合があれば控えめ、なければ目立つ色。どの画面でもショートカット **N** で登録を開く（配合を探すで親・子を選んでいればそれを初期値に。文字の入力中・日本語の変換中・長押し・修飾キーつき・ダイアログや候補を開いている間・ログイン画面では反応しない）。
- 下書き（2026-10-15。register-entry）: 下書きのタブはなくし、配合を探すの全件表示（親・子を選んでいないとき）の条件帯の下に折り畳みの帯「▸ 下書き n 件（この端末だけ）」を出す（0 件でも出す）。頭の行に「すべて登録」「＋ 下書きに追加」（登録のモーダルの下書き版）。開くと、保存の失敗の警告・行の一覧・「すべて削除」（確認なしで消し、トーストの「元に戻す」で戻す）。行は読み取り専用の式（選んでいない枠は「未選択」）・登録者とメモ・理由の文と、「登録」（未選択があれば押せない）・「編集」（モーダル）・「削除」（確認なし＋元に戻す）。開閉は URL の `drafts=1`（履歴は増やさない）。前の `#/drafts` は `#/search?drafts=1` に読み替える。下書きの保存の形（`<namespace>.drafts.<env>.<userIdKey>`）は変えていない（`web/js/ui/drafts-band.js`）。
- 登録のモーダル（2026-10-15。register-dialog）: 上に式の並びの選択欄「親1 ＋ 親2 → 子」と親1・親2 の性別（♂・♀・指定なし。任意。その枠のパルを変えるとその枠の性別だけ空に戻る）、下は左に登録者（自分を先頭、残りは五十音順）とメモ・エラー、右に参照列（高さを固定した確認の枠「この組み合わせは登録済み: 子」〔子の絵を押すと子の欄に入る。別の子が登録済みなら警告の色〕・その親の登録済みの配合・所持パルがあれば親の所持数）。開くと最初の未選択の欄にフォーカスし、検証に失敗したら最初の未選択の欄に印を付けて移る。新規の入力があるまま ×・Esc・キャンセルで閉じたら下書きに残し、トースト「下書きに残しました」の「破棄」で消せる（編集・下書き版・続けて登録の直後・初期値のままでは残さない。残せないときは閉じない）。下書きの親の性別は、前の版のタブが下書きのキーを書き直しても消えないよう、別のキー `<namespace>.draftGenders.<env>.<userIdKey>` に下書き id ごと（親の ID も控え、親が変わった枠の性別は捨てる）に持ち、帯から登録すると記録に入る（`web/js/drafts.js`）。ID の変更で移す。

### 共有の世代とセーブの識別（2026-10-16 追加。sync-fixes の owned-gas）

GAS の共有の書き方を「シート全体を消して書き直す」から**世代ごと**に変えた（`gas/Owned.js`。設計は `docs/sync-fixes/README.md` の 3）。

- **書き込み（F1）**: 鍵の中で ①新しい世代の行（`updatedAt`＝サーバーの時刻）を `OwnedPals` の最後の行の下に足す → flush → ②`OwnedWorlds` の行の `uploadedAt` をその時刻にする（ここで公開）→ flush → ③そのワールドの「今と 1 つ前」以外の世代の行を塊ごとの `deleteRows` で消す。他のワールドの行は触らない。シートの行数（`getMaxRows`）が足りなければ `insertRowsAfter` で 1000 行の余裕をつけて足し、行を消すときは同じ数の空の行を末尾に足し戻す（シートの行数は減らさない。巻き戻し先の版 10 は行数を足さずに全部の行を消してから書き直すので、行数が足りないと消した後の書き込みに失敗して共有が空になる。読み手の範囲が行数を超えないためでもある）。
  - 読む側（`owned`・`ownedSince`）は `updatedAt` が `uploadedAt` と同じ行だけを使う。数が `palCount` と違えば（読む途中で読めなかったときも）1 回だけ読み直し、それでも違えば再試行できるエラー `PARTIAL`（画面は「共有の書き込みと重なりました。少し待つと自動で読み直します。」）。シートの行を直接消したときも `PARTIAL` になる（次の共有で直る）。
  - ③が失敗しても共有は成功のまま（応答の `cleanup: false`）。残った世代・②の前に落ちた行（公開されない孤児）は、そのワールドの次の共有（書かない結果でも）で消える。`OwnedPals` には、そのワールドの行が一時的に 2 世代分ある。
  - 削除（`ownedDelete`）は先に `OwnedWorlds` の行を消し（公開をやめる）、その後で所持パルの行を塊ごとに消す。
- **セーブの識別と結果の種類**: 画面は送る `world` の中に `saveStamp`（`Level.sav` の中の保存時刻の生のティック）・`contentHash`・`format`・`fileCount`・`missingCount`・`force` を入れる（2026-10-16 の share-upload から送る。最上位の項目は増やさないので、古い GAS は捨てるだけ）。`contentHash` は送る中身の SHA-256 の 16 進（画面の `crypto.subtle`。元の文字列は `web/js/core/owned.js` の `ownedContentText` で、`[worldId, ワールド名, ホスト名, ゲーム内の日数, players, bases, farms, columns, items, rows]` の JSON。items は在庫〔2026-10-19 の server から。在庫を送らない形では入れず、前と同じ文字列〕。識別の項目・送った人・`saveUpdatedAt`〔同期で変わる更新日時〕と、追加の情報の `clock`・`saveKind`・`formers` は入れない。並びによらないよう、行は行の JSON の順〔先頭が個体 ID〕、players・bases・farms は要素の JSON の順、object は鍵の名前の順に並べ直す〔個体の並びは登録したファイルの順で変わり、PC ごとに違うことがある〕。セルは文字列。古い GAS に合わせて列を狭めて送るときは狭めた後の中身）、`format` は共有の形の版（`core/owned-shared.js` の `OWNED_FORMAT`。今は 10〔2026-10-19 の server で 4 から上げた〕。列を狭めて送るときは外した列の数だけ下げる＝全部の列で送り直したときに `resent` で書き直される。列を足したら 1、列を足さずに形を変えたら `OWNED_ADDED_FIELDS` の数＋1 上げる）、`fileCount` は読めたファイルの数（`GlobalPalStorage.sav` も数える。`LocalData.sav` は数えない）、`missingCount` は登録してあるのに読めなかったファイルの数、`force` は登録の確定から送るときだけ `true`。GAS は `OwnedWorlds` の列 `saveKey`（`uploadedAt|stamp|hash|format|fileCount|missingCount`）に残し、応答の `result` で結果を返す（`stored` も今どおり）:
  - `new`（ワールドがない）・`newer`（届いた方が新しい）・`stale`（古い。書かない）・`unchanged`（同じセーブ・同じ識別。書かない）・`resent`（同じセーブで、同じ人の送り直しの中身がよくなった、または登録の確定〔`force`〕で悪くならない）・`same`（同じセーブの別の人・古いタブの劣った中身。書かない）。
  - どちらかに識別がない（古い画面・列を足す前・古い版の GAS が後から書いた行〔`saveKey` の先頭の `uploadedAt` がその行と違う〕）は、今までどおりセーブのファイルの更新日時で比べる（新しければ `newer`、古ければ `stale`）。同じ時刻は、今の行に識別があり届いた方にない（古い画面）なら `same`（書かない。同期を受け取った PC の古いタブ〔中身はプレイヤーの入れ替え後・登録が少ない〕が、ホストの完全な共有を同じセーブの劣った中身で上書きしないため。2026-10-17 の sync-fixes の最終レビュー）、今の行に識別がなければ今どおり上書き。古い画面（main）は `stored: false` を「共有されているセーブの方が新しい」として 1 回読み直すだけで、次に新しいセーブを読むまで送り直さない。書いたら `saveKey` は届いた値（なければ空）。
  - 応答の `world` は今公開されているワールド（`saveStamp`・`uploadedBy` を含む）。新旧の比べ方は画面と同じ関数（`web/js/core/owned-shared.js` の `compareSaves`・`decideOwnedUpload`）。手元と共有のどちらを出すか・自動登録の記録の新旧も `compareSaves` で比べる。
  - **前提: 仲間が全員同じタイムゾーン（日本時間）で遊ぶ**。保存時刻はホストの PC のローカル時刻なので、別のタイムゾーンの人がホストすると交代の前後の新旧を誤る。PC の時計のずれは、交代の間（ゲームの終了と同期の時間）より小さい前提。
- **G（`ownedSince`）**: `{ worldId, uploadedAt, presence? }` → 変わっていなければ `{ changed: false, uploadedAt, uploadedBy, saveUpdatedAt, palCount, saveStamp, presence }`、変わっていれば `owned` と同じ中身＋`changed: true`・`presence`。画面は共有の読み直しで呼ぶ（テーマ 4 の share-fetch。下の「共有されたデータは…」。`presence` は 60 秒に 1 回載せる＝下の「ページを開いている PC」）。古い GAS は `BAD_ACTION`（画面は 1 時間、今までの 2 回呼びに落とす）。
- **ページを開いている PC（`presence`）**: CacheService に、ページごとのキー `presence:<env>:<worldId>:<pageId>`（6 時間）と、ワールドの索引のキー `presence:<env>:<worldId>`（1 ワールド 50 件）。索引の更新は ScriptLock を 0.5 秒だけ試す（Web アプリの実行では DocumentLock が使えないため。取れなければ索引だけを諦め、次の送信で戻る）。値は `{ user, device, role, playing, canShare, at }`（`at` はサーバーの時刻）と、サーバーの PC の常駐が送ったときだけ `resident: true`（2026-10-19。server。真偽値でなければ presence の操作は `VALIDATION`、`ownedSince` に載せたものは記録しないだけ。版 12 の GAS は知らない項目として捨てて記録する）。キャッシュの失敗は本体の操作を失敗させない（一覧は `null`）。名前と役割は自己申告。画面から送る動きと表示は下の「ページを開いている PC」。
- **停止の印と圧縮**（巻き戻し用。GAS の編集画面から実行）: `compactOwnedTest()`・`compactOwnedProd()`（＝`compactOwned('test'|'prod')`。引数のない `compactOwned()` は何もしない）は、その環境の停止の印（Script Properties の `OWNED_PAUSED_<env>`）を立て、全ワールドを今の世代だけにし、`saveKey` の列を空にし、いちばん大きいワールドが倍になっても版 10 が書ける行数の余裕を残す。印が立っている間、新しい版の `ownedUpload`・`ownedDelete` は何も書かずに `BUSY` を返す（巻き戻しの後に遅れて届いた呼び出しが世代や `saveKey` を書き戻さないため）。`resumeOwnedTest()`・`resumeOwnedProd()` で印を消す。

#### GAS の反映（ユーザーが行う。P0 の後に本番）

3. 版を作り、テスト用の deployment を作る: `npx clasp create-version "owned-gas"`（版 11 になるはず）→ `npx clasp create-deployment -V 11 -d "owned-gas test (sync-fixes)"`（表示された deployment ID がテスト用。URL は `https://script.google.com/macros/s/<テスト用 ID>/exec`）。テスト用と本番は同じスプレッドシート・同じ鍵とキャッシュを使い、パスワードでシートを分けるだけなので、**計測は遊んでいない時間に**。
4. 計測（テスト用パスワードと `.env.local` の `PAL_TEST_PASSCODE`。テスト環境だと確かめてから書き、自分のランダムな worldId だけを消す）:

#### 巻き戻し（本番を版 10 に戻す）

1. `npx clasp update-deployment <本番の ID> -V 10 -d "rollback"`（ID は上の「デプロイ情報」と照らす）。画面は戻さなくてよい（新しい画面は版 10 でも動く。`ownedSince`・ページを開いている PC は `BAD_ACTION` で 1 時間ずつ止まる）。
2. GAS の編集画面（HEAD のコード）で `compactOwnedProd()`（停止の印を立ててから、今の世代だけにして `saveKey` を空にする。遅れて届いた新しい版の呼び出しは印を見て書かない）。
3. 共有を読み、2 世代が残っていない・`saveKey` が空なことを確かめる。戻してから圧縮するまでの間は、版 10 が世代を見ずに読むので、画面に 2 世代が重なって見えることがある（そのワールドの次の共有でも直る）。古い版は `saveKey` を書かないので、圧縮の後は空のまま。
4. 新しい版に戻すときは `resumeOwnedProd()` → `npx clasp update-deployment <本番の ID> -V 12 -d "owned-gas"`。最初の共有は更新日時の比較で動く（古い版の行の `saveKey` は識別として使わない）。

### 設定（設定タブの「セーブ連携」）

- 設定の並び（2026-10-15 の settings）: セーブ連携 → アカウント（「ログイン中: X」と「ID を変更」「ログアウト」。名前の変更の説明は変更のモーダルだけ）→ データ（整合性の警告〔0 件ならカードごと隠す。1 件以上なら「整合性の警告（n 件）」とレールの設定のタブに赤い数。タブの行き先は `#/settings?open=warnings` で警告のカードの見出しへ〕・書き出し〔配合の CSV・所持パルの CSV〕・この端末のデータ）→ このアプリについて（小さな文字の権利表記と、配信版のときだけ版の短いハッシュ）。左寄せ（前は中央寄せ）。前の「データの状態」カード（環境・前回取得・「最新に更新」）は、ヘッダーの同期状況（押すと最新に更新）で代わるのでなくした。「通知」カードは bell でなくした。
- この端末のデータ（`web/js/device-data.js`。F081）: 下書き・目標・通知の既読・自動登録の記録の件数と「書き出す」「読み込む」。書き出しは `pal-note-device-<環境>-<日付>.json`（`format: "pal-breeding-note/device-data"`・`version: 1`・環境・ID・下書き〔保存の形〕と親の性別の対応・目標・観測・既読の id・自動登録の通知・前の版のプレイヤーの対応〔この端末の localStorage の分。2026-10-19 の server から、GAS のシート `PlayerMap` の対応はノートにあるので含めない〕）。**含めないもの**: パスワード・記録のキャッシュ・所持パル（セーブから読み直せる）・自動登録の牧場の記録（端末をまたぐと照合を取り違える）・理想個体の計画の記憶・画面の状態。読み込みは 1MB まで、形式・版・環境（テスト／本番）が違えば断り、ID が違えば確かめ、件数の確認の後に**今のデータに足す**（下書きは id で和・今のものを優先、目標は同じ条件と上限 100 件を除いて足し〔ワールドの完成は持ち込まない〕、観測は和、既読は和、自動登録の通知は同じ id を除いて足し、プレイヤーの対応は今の値を優先。読み込んだ対応は前の版の対応に足し、GAS で動いていれば次の読み直しで GAS にない分だけ上げる〔下の「プレイヤーの対応（PlayerMap）」の移行〕）。書き込みは各ストアの関数（`drafts.importMany`・`ideals.importGoals`・`notifications.markRead`・`autoRegister.importNotices`・`autoRegister.setLegacyMapping`〔前の版の対応に書く。GAS の対応を書く `setMapping` ではない〕）を通す。ログアウトの確認文に「下書き・目標・既読などはこの端末に残ります（同じ ID でログインすると戻ります）」。
- セーブ連携のカードの状態の行は、役割（ホスト・参加）の短いチップと読み込みの状態・「読み込みを許可」・「今すぐ読み込む」。前の状態の一覧（この PC・表示中・更新）は、表示中と更新がヘッダーと所持パルで見られるのでなくした。登録したワールドの行は「「テスト」（ホスト Alice） · 10/10 09:00 に遊んだ」（参加のワールドは「参加」のチップ）で、編集・削除は開閉の部品（summary）の外の右端。登録のモーダルの結果欄は 2 行分の高さを保ち、チェックリストの各行に貼ったパスから作った実際のパス（長い ID は頭 4 字）を添える。

- 共有はワールドごとに丸ごと置き換える（新しい世代として書き、前の世代は次の共有までに消える）。セーブから消えたパルはシートからも消える。

- どのワールドの・いつのデータか・読み込み中かは、ヘッダーのセーブ連携の状態（「「ワールド」· セーブ 時:分 · 自動登録 オン」。読み込み中は点が流れ、押すと詳しい状態と操作）だけに出す（`ui/save-status.js`）。許可が切れたときはヘッダーのセーブ連携の状態が「許可が必要」になり、押すとその場で許可を求める（理想個体・継承ルートからもここで許可する）。所持パルは下の案内の帯にも「読み込みを許可」を出す。ワールドの切り替え・今すぐ読み込むは設定タブ（とヘッダーのセーブ連携の状態の「今すぐ読み込む」）。
  - 2026-10-14 のユーザーのフィードバック（README の D29）で、所持パル・理想個体・継承ルートに出していたデータ元の 1 行（ワールド・この PC／共有・体数・セーブの時刻・最終確認・「読み込みを許可」・「設定 →」）は、ヘッダーと重なるのでなくした（設定タブへは左のナビから行ける）。
- 所持パルのタブの案内の帯は、対応が要るものだけ（読む許可・読めないエラー・共有の失敗・読めなかったファイル・登録されていないプレイヤーのファイル・パル次元ストレージの読み漏れ〔下の「登録した後に仲間が増えると」の次の項目〕・場所が分からないパル〔「見る」で場所「不明」に絞る〕・セーブの一部を読めなかった）。案内は 1 文と行き先のボタン（「設定タブの〜」とだけ書かない。2026-10-14 の copy-dead-ends）: 所持パルのデータがなく自動の読み込みもオフのとき（と、自動の読み込みで登録が 1 つもないとき）は「セーブのファイルが登録されていません。」と「ワールドを登録」（この画面のまま登録のモーダル）、読めないエラーは「セーブ連携を開く」（設定のセーブ連携の状態の欄の「今すぐ読み込む」などへ。`web/js/router.js` の `settingsHash` の `status`）、登録されていないプレイヤーのファイルは「ワールドを編集」（そのワールドの編集のモーダル）。参加者の名前が合わない 2 行目が GAS の対応の文（本人が設定で選べる）なら「プレイヤーの対応を開く」（表示しているワールドの設定の未設定の行。`settingsHash` の `registrant`。前の版の、ホストに頼む文には付けない。2026-10-19 の server の最終レビュー）。確かめている・読んでいる間は前の案内のまま（帯が出入りしない）。

### セーブのファイルの登録（自動の読み込み）

- ブラウザ（Chrome・Edge）は `AppData` 配下のフォルダを開けないが、エクスプローラーからドロップした**ファイル**のハンドルは受け取れ、IndexedDB に保存して後から読み直せる（`web/js/save/handles.js`）。以前のセーブ連携ツール（ローカルの中継）は廃止した。
- 登録はワールドごとに 1 回（設定タブの「＋ ワールドを登録」で開くモーダル）。
  1. エクスプローラーでワールドのフォルダ（`%LOCALAPPDATA%\Pal\Saved\SaveGames\<Steam ID>\<ワールド ID>`）を開き、アドレス欄のパスを貼る。セーブのファイルにはワールド ID が入っていないため、パスから ID を取る。
  2. 画面に出る場所のファイルをドロップする（何回かに分けて足せる）。ホストのワールドは `Level.sav`・`LevelMeta.sav`・`LocalData.sav`（必須）と `Players` の中のファイル全部、任意で 1 つ上の `GlobalPalStorage.sav`。参加しただけのワールドは `LocalData.sav` だけ。
  3. ドロップするたびに読み込んで、ワールド名・ホスト名・体数をモーダルに出す（まだ保存・共有しない）。「保存」で登録し、読み込みと共有を始める。貼ったパスとドロップしたファイルが同じワールドかは機械では確かめられないので、ワールド名で確かめる。
- 登録したワールドは、一覧の「編集」でパスを入れた状態のモーダルを開き、足したいファイルをドロップして「保存」する。「削除」で登録を消す（最後の 1 つを消すと自動の読み込みも止まる）。
- 登録した後は、ゲームが保存するたび（タブが裏にあっても。下の「セーブの見張り」）と、10 秒ごとの定期の確認（前に読んでから 20 秒以上空ける。安全網）と、所持パル・継承ルート・理想個体を開いたとき・タブに戻ったときに、登録したワールドの中から最後に遊んだワールドを選び、セーブが更新されていれば読み直す（見張りの知らせと裏のタブの定期の確認では、共有された一覧は取り直さない）。ホストのワールドで `LocalData.sav` だけが変わったとき（ゲームの保存の途中。`Level.sav` はその少し後に書かれる）は読み直さない（解析は `LocalData.sav` を読まないので同じ中身になる。読み直すと同じ中身を送り直し、続く新しいセーブの共有が遅れる。`save/handles.js` の一覧の `readSignature`。2026-10-17 の sync-fixes の最終レビュー）。別のワールドに固定するときは設定タブの「使うワールド」で選ぶ。
- 読む許可: 初めて読むとき（またはブラウザを開き直したとき）に Chrome が許可を求める。「毎回のアクセスを許可」を選ぶと、次からは確認なしで読む。**「今回のみ」で許可すると、タブがしばらく裏にある間に Chrome が許可を外すことがある**（外れるとセーブの読み直しが止まり、共有も自動登録も止まる。何分で外れるかは実機で確かめていない）ので、「毎回のアクセスを許可」を勧める。許可が要るときは、ヘッダーのセーブ連携（「許可が必要」。押すとその場で許可を求める）・所持パルの案内・設定の状態の行に、同じ文「セーブを読む許可が必要です」と止まった時刻（「14:32 から読めていません。この間に拾ったタマゴは自動登録されていない場合があります」）と「毎回のアクセスを許可」の勧めを出し、「読み込みを許可」ボタンを置く（`web/js/ui/owned-status.js` の `permissionNotice`。止まった時刻は `owned.js` の `state.auto.stoppedAt`。2026-10-15 の autoreg-visibility）。許可のないワールドがあるときは、別のワールドを黙って選ばない。許可されなかった（拒否・一部だけ）ときはトースト「許可されませんでした。Chrome のサイトの設定で許可を戻すか、ファイルを登録し直してください」。
- 読み込みが止まっているとき（許可待ち・読めない・登録なし）は、左のナビの所持パルのタブに警告の色の「!」（読み上げは「所持パル（読み込みが止まっています）」）。
- 題名とファビコン（`web/js/attention.js`。2026-10-15 の autoreg-visibility）: 題名は「画面名 · パル配合ノート」（パル詳細はパルの名前）。タブが裏にある間だけ、要確認の未読（ベルの赤い数字と同じ数え方。更新内容のお知らせは数えない）があれば題名の頭に「(3) 」、読み込みが許可待ちで止まっていれば「(!) 読み込み停止 · 」を付け、ファビコンの右上に赤い丸（1〜9・「9+」、止まっているときは「!」）を重ねる。表に戻ったら元に戻す。ファビコンは `web/favicon.svg` の 2 つの path を定数で持ち（favicon.svg を変えたら attention.js も直す）、data: の SVG にして差し替える（今の CSP の `img-src 'self' data:` で許されている）。
- 自動登録のトーストに「見る」（1 件ならその組、2 件以上なら更新日の新しい順の配合を探す）。自動登録しなかったタマゴ（照合が合わない）の通知は、押すと配合を探すでその親の組（新しく出る通知から。前に保存した通知には付かない）。
- 登録待ち（設定のワールドの行の、登録者の選択のすぐ上）: 登録されずに残っている候補を「登録待ち 3 件（登録者未設定 2・登録済みと違う 1）」で出す（0 件なら出さない。共有の結果を待っている保留の候補は数えない。下の「ホストの交代」）。「登録済みと違う」の行は親 2 体の絵・「登録を開く」（配合を探すでその組）・「破棄」（確かめてから。その候補を自動登録しない）。登録者未設定はすぐ下の登録者の選択で片づくので数だけ。**候補の子（配合表で決めた値）は出さない**（`auto-register.js` の `pendingSummary` は親と理由だけを返し、破棄に使う ID も子を含まない）。
- 読み込みで飛ばすのは、必須（`Level.sav`・`LevelMeta.sav`・`LocalData.sav`）以外の消えたファイルだけ（所持パルのタブに知らせる）。ただし、飛ばす前にまず採用を保留して読み直し、30 秒たっても同じなら飛ばす（保存の途中の置き換えで一時的に消えただけかもしれないため。下の「セーブの見張り」の「読み直しの保留」）。読めないエラー（許可・ゲームの保存中など）は失敗にし、共有もしない。必須のファイルが読めないワールドは、ホストか参加かを判定せず、共有を止める。選んでいなければ、読めるワールドのうち最後に遊んだものを読み、読めないワールドがあれば知らせる。
- 共有は、このページでホストのワールドのセーブを正常に読めたときだけ行う（開き直した直後は、保存済みのデータがあっても一度読み直す）。読み込みの途中で登録の削除を押した場合、その読み込みの結果では共有しない。
- 1 回のドロップに同じ名前のファイル（同じ場所に入るもの）が 2 つ以上あると、どれが正しいか分からないので、そのファイルはどれも受け取らない。
- 同じワールドかは、ワールド ID（フォルダ名）だけで見分ける。参加すると、自分の PC にホストのワールド ID と同じ名前のフォルダができ、`LocalData.sav` だけが書かれる。ワールドデータを仲間に渡すときにフォルダごとコピーすれば ID は変わらないので、誰がホストしても同じワールドとして扱える（前にホストしたワールドに参加すると、更新日時で参加と判定する）。フォルダ名を変えると別のワールドになる。
- 一度もホストしていないワールドに参加するときは、そのワールドの `LocalData.sav` を 1 回登録しておくと、遊んだワールドとして自動で選ばれる。
- 登録した後に仲間が増えると、その人の `Players\<ID>.sav` は登録されていない。所持パルのタブに案内が出るので、案内の「ワールドを編集」（または設定の登録したワールドの「編集」）からドロップして足す。
- パル次元ストレージの中身は、その人の `Players\<ID>_dps.sav`（次元ストレージを使い始めたときにできる）にある。登録の後に使い始めた人の `_dps.sav` は登録されていないので、同じく「ワールドを編集」からドロップして足す（登録のモーダルの「Players\ の中のファイル全部」の行にも添えてある）。2026-10-16 の sync-fixes の dps-missing で、読めていない個体を数えて知らせるようにした:
  - `Level.sav` には全員の次元ストレージの個体の一覧（`InLockerCharacterInstanceIDArray`）がある。そのうち、読めた `_dps.sav` にない個体の数を数える（`web/js/save/palworld.js` の `buildSnapshot` の `stats.inLocker`・`stats.inLockerMissing`。数だけで、個体の ID は残さない。`npm run check:save` の「次元ストレージ: Level.sav N 体・読めていない M 体」）。一覧には誰の分かが入っていないので、欠けを人に割り振れない。
  - ホストの画面（この PC で読んだセーブ）: 読めていない個体があれば、所持パルの案内・ヘッダーのセーブ連携（押す前の説明とパネルの困りごと）・理想個体の結果の上に「Level.sav ではパル次元ストレージに 118 体いますが、27 体を読めていません。Players\XXXX_dps.sav（Bob）が登録されていないかもしれません」と［ワールドを編集］を出す。候補は `Players\<ID>.sav` は読めたのに `_dps.sav` を読めていない人（Lv の分かる人だけ。次元ストレージを使っていない人も入るので「かもしれません」）で、欠けの数は候補の人数で割らない。候補がいなければ「…読めていません（ファイルが足りないか、保存の途中に読んだ可能性があります）」（ボタンなし）。数のない古い保存データでは出さない（分からない）。
  - 参加者: 候補のプレイヤーに欠けの数（`dpsGap`）を付けて共有する（players の JSON の中。列は増えない。古い GAS は黙って捨てるだけで、参加者に案内が出ないだけ）。参加者の画面では、自分のプレイヤー（「このワールドでの自分」→「プレイヤーの対応」→ 同じ名前の順。理想個体と同じ）が候補のときだけ「ワールド全体で、パル次元ストレージの 27 体が出ていません。ホストの登録にあなたの Players\XXXX_dps.sav がないかもしれません。ホストに足してもらってください。」を同じ 3 か所に出す（数はワールド全体の欠けで、あなたの分とは限らない。ファイルが複数なら「、」で区切る）。ほかの人が候補のときは出さない。
- IndexedDB に保存できないブラウザ（シークレットウィンドウなど）では、ページを開いている間だけ使う。
- Firefox など、ドロップからハンドルを取り出せないブラウザでは、Chrome か Edge で開くよう案内する（フォルダからの手動の読み込みは 2026-10-06 に廃止した）。
- ゲームの保存の途中に読むと失敗することがある。見張りの知らせで読んだとき・見張りが動いている間の定期の確認では自動で読み直す（下の「セーブの見張り」）。Worker を作れないブラウザの定期の確認・「今すぐ読み込む」では失敗になるので、少し待ってから「今すぐ読み込む」を押す。
- 手元のセーブで読み込みを確かめるには `npm run check:save -- "<ワールドのフォルダ>"`（省略すると最後に遊んだホストのワールド）。

### セーブの見張り（2026-10-17 追加。sync-fixes の save-watch）

ゲームの保存（約 30 秒ごと）を見張り、一式を書き終えたところで読み直す。設計と P0 の実測は `docs/sync-fixes/README.md` の「P0 の結果」「P0 で決めたこと」「6. save-watch」。

- 仕組み: 見張りは Worker（`web/js/save/watch.js` の `createSaveWatcher`。`web/js/save/worker.js` の `type: 'watch'`・`'stop'`。解析の Worker とは別に 1 つ）の中で動く。画面のスレッドの `createWatchClient` が、見張る対象（`web/js/owned.js` の `watchTargets()`）を世代番号と組で送り、違う世代の知らせは捨てる。
  - 対象: 登録したワールドのうち、直近の一覧で許可があったもの（保存の途中などで一時的に読めないワールドも外さない。外すと戻ったことに Worker が気づけない）。「使うワールド」を選んでいればそのワールドだけ。今のワールド（連携しているワールド、なければ最後に遊んだワールド）は登録した全ファイル、ほかのワールドは `Level.sav`・`LocalData.sav` だけを 5 秒ごとの確認で（最後に遊んだワールドが替わったことに気づくため。数秒遅れても困らないので Observer は使わず、Chrome が押さえるフォルダを今のワールドの 1 つにする）。同じ対象（ワールド・パス・登録の版・今のワールドか）なら送り直さない。自動の読み込みが無効・対象がなければ Worker を止める。
  - **FileSystemObserver で見張るのは、今のワールドのフォルダの直下のファイル（`Level.sav`・`LevelMeta.sav`・`LocalData.sav`）だけ**。`Players` の中（`<ID>.sav`・`<ID>_dps.sav`）と `GlobalPalStorage.sav` は Observer に渡さず、Worker の 5 秒ごとの `getFile()` の確認だけで拾う。理由: Chrome は見張っているファイルの入ったフォルダを押さえる（ファイルが消えた後も 0.5〜2 秒）ので、`Players` の中を見張っていると、SaveSync が同期を受け取るときに `Players` を消せずに止まり、ワールドのフォルダが `LocalData.sav` だけになる（2026-10-17 に実際に起き、作業用のフォルダで再現した）。直下のフォルダは `LocalData.sav` が残るので SaveSync に消されない。`getFile()` と中身の読み込みはフォルダを押さえない。画面側（`watchTargets()` が Observer に渡す印 `observe` を直下のファイルだけに付ける）と Worker 側（`observable(path)` で絞る）の 2 か所で守り、`Players`・`GlobalPalStorage.sav` のハンドルが `observe()` に渡らないことをテスト（`test/save/watch.test.js`・`test/web/owned-store.test.js`）で確かめている。**`Players` の中を Observer で見張る変更はしない**。
  - 方式: Observer が使えれば Observer（ワールドごとに 1 つ。どのファイルの通知かは `root` の名前で見分ける）。ゲームはファイルを置き換えて保存するので、保存のたびに `disappeared`・`errored`（まれに `appeared`）が来る（P0）。そのたびに変化として数え、`getFile()` が通ってから `observe()` し直し（10・50・250・1000 ms の段）、直後に照らし合わせる。4 段で張り直せないファイル（と、始めたときにファイルがなく見張れなかったファイル）は 5 秒の確認だけにし、5 秒ごとの確認でファイルが戻ったのに気づいたら張り直す（SaveSync の同期の受け取りでファイルが消えても、読み込み直さずに戻る。消えている・読めない間は張り直しを試さない。Observer に渡すのは上の直下のファイルだけのまま）。`appeared`・`modified`・`moved` はそのファイル、`unknown` はそのワールドの全ファイルを照らし合わせる。5 秒ごとの確認は Observer があっても動き、全部のファイル（`Players` も）を更新日時・大きさで比べる（前の回が終わっていなければ飛ばす。Worker の中のタイマーは裏のタブでも 5 秒のまま。P0）。Worker を作れないブラウザは、`app.js` の 10 秒ごとの定期の確認（セーブは 20 秒以上空ける。タブが長く裏にあると Chrome が 1 分に 1 回まで遅らせる）だけ。
  - 一式の書き終わり: ワールドごとに、最後の変化から 1 秒（`quietMs`）静かになったら、または最初の変化から 10 秒（`maxWaitMs`）で、全ファイルを照らし合わせ、前に知らせたときから変わったファイルを画面に知らせる（`settled`）。ホストのワールド（`Level.sav` を登録したワールド）は、`Level.sav` の変化を見るまで 1 秒を数えない（`LocalData.sav` は `Level.sav` より最大 2.74 秒早く書かれ、`Level.sav` から後は数 ms でそろう。P0）。画面は `owned.refreshFromWatch(worldId)` で読み直す（共有は読み直さない。読み込み中・順番待ちなら、終わった後に 1 回だけ）。許可が外れた（`NotAllowedError`）ことも 1 回だけ知らせ、読み直しが許可待ちにする。
- 読み直しの保留（見張りの知らせでも、ページを開いた直後の最初の読み込みでも、定期の確認でも同じ。`owned.js` の `readAuto` が `'held'` を返す）: 読んだ一式を採用せず、前の手元のデータ・表示・共有（取り消した共有の予約・再試行も今のセーブのまま戻す）を残したまま読み直す。
  - 読む前と後でファイルの印（更新日時・大きさ）が違う（保存の途中に読んだ。P0 で 1 回、`Level.sav` と `LevelMeta.sav` が 30 秒食い違った）: 1 秒後。
  - 登録したファイルの読み・解凍・解析の失敗と一時的な消失（所持パルの案内の「〜を読めませんでした」になるもの）: 最初に見た時刻から 1・3・10・30 秒。30 秒たっても同じ形（パスと理由の集合）なら、壊れた・消えたとみなして今までどおり飛ばして読み、案内を出して共有する（新しいセーブなら欠けたまま `newer` で載り、後でファイルが戻れば `missingCount` が減って `resent` で直る）。受け入れた形はワールドごとにページの中だけ覚え、同じ形なら次から待たない（消したままのファイルで毎回 30 秒遅れない）。全部読めたら忘れ、形が変われば待ち直す。登録の確定（登録のモーダルで読んだ結果）はすぐ採用する。
  - 見張りから読んだときの読めない失敗（ゲームの保存中〔`NOT_READABLE`〕・必須のファイルの一時的な消失・`Level.sav` を読めない／解析できない）: エラーを出さず、別のワールドに替えたり止めたりせずに、最初の失敗から 1・3・10 秒で読み直す。3 回目もだめなら今までどおりの扱い（エラーの案内）。見張りが動いている間（Observer か Worker の 5 秒ごとの確認）は、定期の確認（`app.js` の 10 秒ごとのタイマーの `autoRefresh`・`pollAuto`）も同じに扱う（保存の途中に当たっても止めたり別のワールドに替えたりしない。2026-10-17 の sync-fixes の最終レビュー）。Worker を作れないブラウザ（定期の確認だけ）では今までどおりすぐ失敗にする。
  - 読み直しのタイマーは 1 本。別のワールドに替わった・登録を消した・採用できたら止める。
  - 「今すぐ読み込む」（ヘッダーのセーブ連携のパネル・設定）で保留になったときは、トースト「セーブの一部をまだ読めないため、少し待ってから自動で読み直します」（`ui/owned-status.js` の `refreshNow`。何も起きないように見えないように）。
- 確かめ方: ヘッダーのセーブ連携のパネルの「監視」の行（自動の読み込みが有効で登録があるときだけ。参加者は `LocalData.sav` をゲーム中の推定のためだけに見張り、セーブは読まないので出さない）。「ファイルの変更」（Observer）・「5 秒ごとの確認」（Worker の確認だけ）・「定期の確認（タブが裏だと 1 分ごと）」（Worker を作れない）と、今のワールドの「最後の保存 12:03:30（7 ファイル・0.8 秒）」（書き終えた時刻〔変わったファイルの更新日時の最大〕・変わったファイルの数・書き始めから書き終わりまで）。
- 見ていないこと（実機で確かめる）: Edge、受け取る側の PC で SaveSync が直下のフォルダそのものを作り直すことがあるか、ゲームでワールドを削除するときに直下のファイルの見張りが邪魔をしないか。

### ホストの交代（SaveSync）（2026-10-17 追加。sync-fixes の host-rotation）

ホストは仲間内で交代する。ゲームを終えると SaveSync（Steam）が、ワールドのフォルダ全体を全員の PC に同期する。設計と実測は `docs/sync-fixes/README.md` の 7 と「P0 の結果」。

- **全員が一式を登録しておく**: 交代でホストする人も、`Level.sav`・`LevelMeta.sav`・`LocalData.sav`・`Players` のファイルを登録しておく（登録のモーダルの組の見出しは「ホストする PC（交代でホストする人も）」。参加者として登録したワールドの行と、参加者として登録するときの結果欄にも、［編集］で足すよう出す）。`LocalData.sav` だけの登録のままホストすると、その PC のページはセーブを読めず、共有も配合牧場の自動登録も動かない（参加者の画面に下の「共有が止まっています」が出る）。
- **役割の判定**: 今までどおり `judgeRole`（上の「設定」の節）。同期を受け取った PC は、全ファイルの更新日時が元の最後の保存の時刻にそろうので、ゲームをしていなくてもホストと判定される。そこで「ゲーム中」を別に推定する。
- **ゲーム中の推定**（`web/js/core/playing.js`。`owned.js` の `state.play`）: 変化の値は、ホストは `Level.sav` の中の保存時刻（登録したファイルから読んだセーブ。登録の確定で読んだものも）、参加者は `LocalData.sav` の更新日時（一覧の `playedAt`。参加者と判定するのは `LocalData.sav` の方が新しいときなので同じ値）。読むたびに値を記録し、見た時刻が直近 2 分の中にある変化のうち、続く 2 回で後の変化の間（値の差）が 20〜90 秒のものがあれば「ゲーム中」（ゲームは約 30 秒ごとに保存する）。
  - 間を見た時刻ではなく値の差で測るので、裏のタブで確認が遅れても、同期で更新日時が元の時刻に戻されても（値が過去に動く）だまされない。受け取る側の PC の同期の書き込みは 1 回の変化なので、続けて 2 回の条件で除ける。
  - ページを開いた直後の最初の読み込みは基準だけ（数えない）。ワールドか役割が変わったとき、今のワールドの見張りの対象が変わったとき（見張りのやり直し。見張っていなかったところから始めるときは除く。ほかのワールドの登録の削除・編集・許可の変化と、一覧の並びの入れ替わりでは数え直さない。2026-10-17 の sync-fixes の最終レビュー）は数え直す。2 分変化がなければ外れる。使うのは、今のワールドと役割が記録と同じときだけ。
  - ヘッダーのセーブ連携のパネルの「この PC」の行の 1 行目（役割の説明の上）: ホストは「ホスト中（推定）」か「ホスト用のセーブあり（ゲームの保存は続けて見えていません）」（同期で受け取った・ゲームを終えた後）、参加者はゲーム中のときだけ「参加中（推定）」。前は「ゲーム」の別の行だったが、「ゲーム内」（日数）と紛らわしいので「この PC」にまとめた（2026-10-17 の sync-fixes の最終レビュー）。
- **セーブの識別と共有の結果**: 上の「共有の世代とセーブの識別」（`Level.sav` の中の保存時刻で同じセーブかを見分ける。結果は `new`・`newer`・`stale`・`unchanged`・`resent`・`same`）。同期の後にゲームをしていない PC のページが送っても、同じセーブは `unchanged`（自分が前に送った）か `same`（別の人が送った）になり、書かない（`uploadedBy` も変わらない）。共有より新しいセーブ（ホストの PC でページを開き忘れて遊んだ分）は `newer` で載る。
- **配合牧場の自動登録**（`web/js/auto-register.js`）: 証拠を集めることと、登録してよいと決めることを分けた。
  - 新しいタマゴの証拠は、今までどおりセーブを読むたびに集め（タマゴの証拠はそのセーブにしかないので、共有の結果を待たない）、「配合のキー＋そのセーブの中の保存時刻（`saveStamp`）」の候補として端末の記録（`<namespace>.autoBreeding.farms.<env>.<ワールド ID>` の `pending`）に残す。候補は `stamp`・`savedAt`・`seenAt`（読んだ日時）・`playing`（読んだときホスト中〔推定〕だったか）・`state`（`hold` 保留／`ok` 登録してよい）を持つ。保存時刻の読めないセーブの候補と、前の版の候補（`stamp`・`state` がない）は `ok`（今までどおり）。ファイルの更新日時だけが新しい同じセーブ（同期で書き換わった）では候補を増やさない。
  - 共有の結果（`owned.js` の `state.upload`。送ったときの環境〔`scope`〕が今の環境と同じものだけ。環境を切り替えた後に残っている前の環境の結果は使わない）が届くたびに、判定 `{ kind, stamp }` を同じ記録の `verdicts`（直近 20 件。同じ判定は 1 回）に足し、その stamp（S）以前の保留の候補を決める（S より後に読んだ候補は、その判定では決めない）。結果が読み込み中に届いても記録し、後で読んだ候補・読み込み直しの後のページにも当てる。識別のないセーブ（stamp が空）の結果は、自分の共有が載ったとき（mine）だけ `{ kind: 'mine', stamp: '', savedAt }` とし、候補の更新日時が送ったセーブの更新日時以前なら登録してよいにする（same・stale は同じセーブかを見分けられないので何もしない。更新日時は同期で書き換わるので、同じセーブの判定には使わない）。記録を書くときは、書く直前の最新の記録の判定と和を取り、書く候補に当て直す（別のタブが同時に判定を足しても消えず、捨てた候補が戻らない）。

    | 共有の結果（`state.upload.status`） | 判定 | 候補 |
    |---|---|---|
    | `done`（自分の共有が載った: `new`・`newer`・`resent`・自分の前の送信が届いていた `unchanged`・古い GAS の `stored`） | mine | S 以前 → 登録してよい |
    | `same`（別の人が同じセーブを共有済み: `same`・他人の `unchanged`） | same | stamp が S の候補 → 捨てる（そのセーブは別の PC の担当）。S より前は保留のまま。公開しているのが送ったときの自分の ID（同じ PC の別のタブ）なら mine |
    | `stale`（別の人が新しいセーブを共有済み） | stale | ホスト中（推定）の間に読んだ候補 → 登録してよい（自分のプレイの証拠）。それ以外は保留のまま（推定が立たなかっただけで、同期で受け取ったとは言い切れない） |
    | `sending`・`error`・なし | — | 保留のまま |

  - 一度登録してよいになった候補は、後の判定で取り消さない（プレイヤーの対応が未設定で待つ候補も消さない）。保留のまま 7 日たった候補は捨てる（読んだ日時から。セーブを読むときと判定のときに）。登録は、登録してよい候補だけを配合のキーごとに証拠をまとめて今までの流れ（登録者の判定・登録済みとの食い違い・通知）で行い、登録したらそのキーの候補（別のセーブの保留の分も）を全部外す。設定の「登録待ち」は登録してよい候補だけを数える。
  - こうなる: 応答を失った S1 の証拠も、後の S2 が自分の共有として載れば登録される。別の人が新しいセーブを載せても、自分の S1 の候補は捨てない（後で自分の共有が載れば登録される）。同期で受け取った同じセーブ（別の人が載せた）の証拠は捨てる。古い GAS（本番の版 10）は stamp を返さないが、`stored` を自分の共有として扱うので今までどおり登録する（同期で受け取ったセーブとは見分けられない）。

  - 確かめ方: 今ホストしている人に、このページを開いているか、ヘッダーのセーブ連携のパネルの「この PC」の行が「ホスト中（推定）」と「このページを開いている間（タブが裏でもよい）、ゲームが保存するたびにセーブを読みます。…」（ホストの説明）になっているかを見てもらう（「ホスト用のセーブあり（ゲームの保存は続けて見えていません）」なら、そのページはゲームの保存を読めていない。「この PC では読み込みません。…」なら、参加者として登録したワールドでホストしている）。参加者の自分が実はホストだった（参加者として登録したワールドでホストした）なら、［ワールドを編集］でホストの組のファイルを足す。

### ページを開いている PC（2026-10-17 追加。sync-fixes の page-presence）

どの PC でこのページが開いているかを仲間どうしで見られるようにした（今ホストしている人の PC でページが閉じていると、共有も配合牧場の自動登録も止まるため）。GAS の側は上の「共有の世代とセーブの識別」の `presence`（CacheService。シートには書かない）。設計は `docs/sync-fixes/README.md` の 8。

- **送る**（`web/js/owned.js` の `reportPresence` と、共有の読み直しの `ownedSince`）: ログインしているページは、今のワールド（表示しているワールド）について 60 秒に 1 回送る。表のタブは 10 秒ごとの共有の読み直し（`ownedSince`）に載せて別には送らない。載せる回がないとき（一覧だけを読む 5 分ごとの回・まだ共有されていないワールド）と裏のタブ（共有を読まない）は、`app.js` の 10 秒ごとのタイマーで、読み直しの後に `presence` を別に送る。
  - 裏のタブはタイマーが 1 分ごとまで遅れるので、送る間隔も広がる（表示は 3 分の幅で見る）。タイマーが少し早く来ても 5 秒の余裕の中なら送る。タブが freeze されると送れない（表示は「最近の応答なし」になる）。
  - ワールド・送る値（役割・ゲーム中・共有できる）が変わったら、間隔によらず次の回（10 秒以内）に送る。ログインしていない・ワールドがないときは送らない。
- **値**: `role`（このページの判定の結果。`host`・`guest`、連携していないワールドは `none`）・`playing`（ゲーム中の推定。上の「ホストの交代」）・`canShare`（このワールドをホストの一式〔`Level.sav`・`LevelMeta.sav`・`LocalData.sav`〕で登録していて、直近の確認で読む許可がある。一覧の確認の後の読み込みで許可が外れ、自動の読み込みが許可待ちで止まっている間も false）・`user`（ログイン中の ID）・`device`（PC の ID。ワールドごとのランダムな値を localStorage の `<namespace>.owned.device.<ワールド ID>` に残す）・`pageId`（ページを読み込むたびにメモリの中で作るランダムな値。sessionStorage は複製したタブで同じ値になるので使わない）。
  - **ID は認証にも本人の証明にも使わない**（共通パスワードの認証なので、名前と役割は自己申告。だれでも別の名前で送れる）。ワールドごとに別の値なので、ワールドをまたいで同じ PC だとは分からない。
- **古い GAS**（本番の版 10）: `ownedSince`・`presence` が `BAD_ACTION` なら、接続先と環境ごとに 1 時間は送らない（`ownedSince` と同じ覚え方。`ownedSince` の `BAD_ACTION` でも覚える）。そのとき前に受け取った一覧も消す（GAS を版 10 に戻した後に、前の一覧が 6 時間出続けない）。送れなくても（通信・`BAD_ACTION`）共有とセーブの読み込みは失敗にしない（次は 60 秒後）。応答の一覧が `null`（サーバーのキャッシュを読めなかった）なら前の一覧のまま。
- **表示**（ヘッダーのセーブ連携のパネルの「ページを開いている PC」の行。1 台 1 行。見出しが長いので、見出しと一覧はパネルの表の幅いっぱいに重ね、ほかの行の見出しの列を広げない。`web/js/ui/owned-status.js` の `openPages`・`openPagesLines`）: 受け取った一覧（`ownedSince`・`presence` の応答。表のタブは 10 秒ごと）を PC（`device`）ごとにまとめる。
  - ●（3 分以内に応答があった PC）: 「Alice · 1 分前 · ホスト中 · 共有できる」。役割（ホスト中・ホスト用のセーブあり・参加中・参加者・セーブ未連携）と共有できるは、その PC の 3 分以内のページの応答だけでまとめる（1 台で複数のタブが開いていれば、ホスト → 参加者 → 未連携の順に選び、ゲーム中はその役割のタブのどれか、共有できるはどのタブか 1 つでも）。
  - ○（それより前）: 「Bob · 最近の応答なし（3 時間前）」。閉じたとは限らない（裏のタブで遅れた・キャッシュが消えた）ので、古いページの役割は出さない。6 時間より前は出さない。
  - 同じ人（ID をそろえて比べる）の 2 台目からは「Alice（PC 2）」（番号は今の一覧〔6 時間以内〕に残る PC の ID の順で、見る人によって入れ替わらない。ID の順で先の古い PC が一覧から消えると繰り上がることがある）。この PC は「（この PC）」。経過はサーバーの時刻で測る（応答のサーバーの時刻＋受け取ってから経った時間。PC の時計がずれていても 3 分の境目がずれない）。
  - 一覧が分からない（古い GAS・まだ受け取っていない・別のワールドの一覧）・6 時間以内の応答がなければ行を出さない。
  - サーバーの PC の常駐（presence の `resident: true`。2026-10-19。server の participant-ui。下の「専用サーバー（ServerSync）と常駐（server-agent）」）: ログインの ID によらず「サーバー」と呼び、「● サーバー（常駐） · 1 分前 · サーバー稼働中」か「… · サーバー停止中」だけを出す（「共有できる」は出さない）。サーバー稼働中は、常駐が送る `playing`（対象のサーバーが動いていて、保存が続いている）。2 台目からは「サーバー（常駐・PC 2）」（番号は常駐どうしで数え、同じ ID のページとは混ぜない）。上の「ホストの交代」の「共有が止まっています」の案内に添える一覧では「サーバー（常駐・サーバー稼働中）」。サーバーは遊ぶときだけ動かすので、停止中はふつうのこととして警告の色にしない。協力プレイに戻した後も常駐が動いていれば行は出る（「サーバー停止中」。協力プレイ中にサーバーが動いている事故に気づけるよう、隠さない）。読み込み直していない古いタブは `resident` を捨てるので、常駐をふつうの PC として「サーバー · ホスト中 · 共有できる」などと出す（配信の後に全員のタブを読み込み直してもらう）。
- **CacheService は期限（6 時間）の前に消えることがある**。消えると、開いているページも次の送信（1 分以内）まで一覧から消えるか「最近の応答なし」に見える（索引の鍵〔ScriptLock を 0.5 秒〕が取れなかったときも同じで、次の送信で戻る）。

### プレイヤーの対応（PlayerMap）（2026-10-19 追加。server の mapping）

セーブのプレイヤー → ノートの ID の対応（配合の自動登録の登録者と、理想個体の「自分の個体」に使う）を GAS のシートに置き、誰の画面からでも設定できるようにした（ユーザーの決定 12・15）。サーバーの PC の常駐も同じ対応を読む。設計は `docs/server/README.md` の T3。

- **置き場所**: シート `PlayerMap`（本番）・`PlayerMap_test`（テスト）。1 行 1 鍵で、列は `worldId`・`key`・`userId`・`playerName`・`updatedBy`・`updatedAt`（`gas/PlayerMap.js`）。`updatedBy` は書いた人の ID（自己申告）、`updatedAt` は GAS の時刻、`playerName` は設定したときのゲーム内の名前（所有者がシートを読むため。画面と常駐が使うのは `userId` だけ）。
  - 外した対応は行を消さずに、`userId` が空の行（墓標）として残す（別の PC の移行が書き戻さないため）。手で同じ鍵の行を足すと、最後の行が使われる。
  - 1 ワールド 200 鍵まで（墓標を含む。鍵を増やして超えるときだけ断る）、1 回の書き込みは 50 件まで。ノートにない ID は断る（`USER_NOT_FOUND`）。
  - 操作は `playerMap`（読む）と `playerMapSet`（書く。`onlyMissing` は GAS にある鍵〔墓標を含む〕を上書きしない。同じ内容は書かない）。ID の変更（`rename`）で、対応の `userId` と `updatedBy` も新しい ID に書き換わる（版 12 に巻き戻している間の ID の変更では書き換わらない）。
- **鍵**（プレイヤーの鍵。`core/owned-shared.js` の `playerKeyOf`・`playerMapKey`）: `i:<キャラクターの InstanceId>`（協力プレイとサーバーを往復して PlayerUId が H ⇔ U と入れ替わっても変わらない）。InstanceId がないとき・ワールドにいない UID は `u:<PlayerUId>`。鍵から UID への解決は `auto-register.js` の `mappingFor` の 1 か所で行う（自動登録の判定はその回のセーブのプレイヤー、表示と設定の欄は今表示しているデータのプレイヤーで引く）。`u:H`（以前のホスト）は、H がワールドのプレイヤーにいないとき（サーバーのワールド）だけ効く（協力プレイのホストと取り違えないため）。InstanceId のない協力プレイのホスト（古いデータ）は選べない。
- **設定の欄**（設定の「プレイヤーの対応」。`views/owned-settings.js`）: ホスト・参加者・未連携で共有を見ている人の誰でも選べる（説明は「…ノートに保存し、仲間と共有します（どの PC からでも選べます）。」）。行はワールドのプレイヤーと、「預けた人」がワールドにいない UID の全員（ユーザーの決定 17。往復すると、協力プレイに戻した後に U も残るため）。後者は「以前のホスト（0000…0001）」「不明なプレイヤー（頭 8 字）」に、小さく「拠点 n 体・牧場 m か所」を添え、下に「以前のホスト・不明なプレイヤーは、今はワールドにいない「預けた人」です。牧場の登録者を正確にしたいときは、親を預け直してください。」。以前の持ち主は、手元のホストのデータならセーブから、ほかは共有の `extras` の `formers` から出す。選ぶと先に反映し、書けなければトーストを出して元の対応に戻す。
  - H は人ではなく「その時のホスト」の枠なので、「以前のホスト」を 1 人に対応づけると、仲間がホストだった時期に預けた分もその人の分になる。正確にしたい牧場は、親を拠点から取り出して置き直す（預けた人が今のプレイヤーになる。`docs/server/README.md` の P0 の M6）。H 以外の UID は人ごとに変わらないので、一度選べば往復しても正しい。
- **読み直し**: 自動登録の判定では 60 秒、設定の欄は描くたびに 15 秒、表のタブは 5 分（`app.js` の 10 秒ごとのタイマー。`ownedSince` には載せない）より写しが古ければ読む。読めなかったときも同じ間隔を空ける。写しは localStorage の `<namespace>.autoBreeding.playerMap.<env>.<ワールド ID>`（常駐は `state.json`）。
- **書くとき**: 同じワールドへの書き込みは 1 つずつ順に送る。送っている途中の対応は表示にだけ出し、自動登録の判定には GAS に書けた対応だけを使う（対応を保存している間は自動登録が待ち、保存に失敗したらその対応では登録しない）。
- **前の版の対応からの移行**: 前の版の対応（この端末の localStorage の `<namespace>.autoBreeding.players.<env>.<ワールド ID>`。uid → ID）は、その端末で GAS の対応を読めたときに一度だけ `onlyMissing` で GAS に上げる（印は `<namespace>.autoBreeding.playersMigrated.<env>.<ワールド ID>`。上げられなかったら 60 秒空けてやり直す）。上げ終えるまでは、GAS に鍵のないプレイヤー（H を除く）にも前の版の対応を使う（「未設定」が出ないように）。
  - **H の対応を上げるのは、その PC がホストとして遊んでいる（手元のセーブの保存が続けて見え始めるまで約 1 分）ときだけ**（同期で受け取った仲間のホストのセーブの H は別の人のキャラクターなので、この PC の前の H の対応を付けないため。「このワールドでの自分」の移行と同じ決め方）。上げられなかったときは H を除いた印を書いて H だけ残し、後でホストとして遊んだときに上げる。上げ終えるまでは、ホストとして遊んでいるときの自動登録の判定に限って前の版の H を使う（その間、設定の欄と登録待ちでは H が未設定に見える）。
  - 配信の手順の「最後にホストした PC で最初に開く」で、H 以外の対応はその PC から上がる。H は、それぞれの PC でホストとして遊んだときに、そのときのホストのキャラクターの鍵で上がる（交代でホストする人は、自分がホストして遊んだときに自分の H が上がる。`onlyMissing` なので、先に上がった鍵は上書きしない）。
- **古い GAS**（版 12。`playerMap` を知らず `BAD_ACTION`）: 接続先と環境ごとに 1 時間覚えて、前の版の対応（この端末だけ。ホストの画面だけで選べる）で動く。`setup()` の前（シートがなく `SHEET_HEADER`）も前の版の対応で動く。版 12 に巻き戻すと前の版の対応に戻る。その間に選んだ対応（前の版の対応に書く）は、版 13 に戻した後の読み直しで、GAS に鍵がない分だけ上がる（前の版の対応が変わると上げた印と合わなくなり、`onlyMissing` でもう一度上げる）。GAS にもう鍵がある対応をその間に変えた分は上がらずに GAS の値に戻るので、版 13 に戻した後に設定で選び直す（H は、その PC でホストとして遊んだときだけ上がる）。巻き戻しの前に GAS に上がった対応はシートに残り、版 13 に戻すとまた使う。
- **この端末のデータ**（書き出し・読み込み）には前の版の対応だけが入る（GAS の対応はノートにある）。読み込んだ分は前の版の対応に足し、次の読み直しで GAS にない分だけ上がる。
- 確かめ方: `PAL_API_URL=… node scripts/api-check.mjs` が対応の読み書き（上書き・墓標・`onlyMissing`・ノートにない ID）を確かめる（`Users_test` に ID がないと一部を飛ばす〔SKIP〕。ダミーのワールド ID `00000000000000000000000000C0FFEE` に墓標の 2 行が残る）。

- プレイヤーの対応は GAS のシート `PlayerMap` に置き、どの PC の画面からでも設定する（上の「プレイヤーの対応（PlayerMap）」）。サーバーでは自分のキャラクターの PlayerUId が H（`00000000…0001`）から作成者の UID（U）に替わるが、対応と「このワールドでの自分」はキャラクターの InstanceId の鍵（`i:`）なので外れない。H は「以前のホスト」の行になる。
- 共有の `extras` の `saveKind`（`server`・`coop`）が、最後の共有の種類。画面のサーバー向けの文言は、これが `server` のときだけ（下の「参加者・閲覧者の画面（サーバーのとき）」）。
- サーバーにしたので: グローバルパルボックスは出さない（サーバーには `GlobalPalStorage.sav` がない。ユーザーの決定 10）。REST の状態表示・通知の共有・ゲーム内アナウンス・今すぐ保存は入れていない（決定 9）。

### 常駐の動き

- **サーバーが動いているか**（`tools/server-agent/server-state.mjs`）: 第一に、ServerSync のローカル API の `GET http://127.0.0.1:54866/instances/<インスタンス ID>` の `status.running` と `pid`（`status.state` は、起動の後も誰かが接続するまで `Starting` のままなので見ない。P0 の M10）。応答には起動の計画（管理者パスワードを含みうる）が入るので、status の 3 項目だけを取り出して残りはすぐ捨てる（ログ・例外の文・状態に残さない）。
  - running と言われても、pid がこの PC で生きていて、対象のインスタンスのフォルダの下の PalServer の実行ファイルが動いているかを PowerShell（`Get-CimInstance Win32_Process` の ExecutablePath）で確かめる（同じ pid でも 30 秒で確かめ直す）。ServerSync の共有で、別の PC が動かしているインスタンスの写しを読んで送らないため（ログの理由 `serversync:not-here`）。
  - ServerSync に届かないときは、実行ファイルのパスだけで決める（30 秒に 1 回）。どちらでも決められなければ `unknown`（共有と自動登録をしない）。
  - 止まってから 60 秒は動いているとみなす（猶予。最後の保存を拾う）。
- **動いている間**（attach）: ワールドを登録して読む。見張りは 5 秒ごとの stat だけ（Observer を使わず、フォルダもファイルも開いたままにしない。ServerSync のバックアップ・同期を止めない）。10 秒ごとに `Players` に増えたファイルを足す（新しく参加した人）。5 分ごとに配合の全件を読み直す。共有は画面と同じ規則（`owned.js` の `uploadLocal`。30 秒ごとの保存のたびに送る。状態が保存のたびに変わるので「同じ中身なら送らない」は入れていない。P0）。
  - 新しく参加した人のファイルを足すと、ゲーム中の推定を数え直すので、1〜2 分は presence の playing が false になることがある。
  - 名前: サーバーのセーブの名前は汎用の `Autosave_W` なので使わず、設定の `worldName` → 前の共有の名前の順。ホスト名は空。
- **止まったら**（detach）: 見張り・読み直しと送信の予約・自動登録の判定を止める。止まったと確かめたとき（`stopped`）だけ、最後の保存の送信を最大 60 秒待つ（通信の失敗と判定待ちは 15 秒おきに送り直す。送れなければ、次に動いたときの読み込みで送る）。動いているか確かめられない（`unknown`）ときは、最後の送信をせずにすぐ止める。止まっている間に来た読み直しの予約は、次に動いたときに実行する。止まっている間の自動登録はしない（決まった候補は state.json に残り、次に動いたときに登録する）。
  - 前に動いていた間に読んだセーブは、次に動いたときの判定・共有・自動登録に使わない（動いた後に読み直したセーブから使う。A → B → A の引き継ぎで、B の続きを受け取る前の古いデータで止めたり送ったりしないため。ログの upload に `AGENT_STALE` が出ることがある）。動き出したときにディスクのセーブが前と同じなら、次の保存（約 30 秒後）まで共有が遅れる。
- **presence**: 常駐が自分で 60 秒ごとに送る（playing・canShare が変わったらすぐ。止まっている間も送る）。値は `role: 'host'`・`resident: true`・`playing`（サーバーが running で、保存が続いている）・`canShare`（読み込んでいて止まっていない）。PC の ID（`device`）は state.json の `pal-note.owned.device.<ワールド ID>`。画面の表示は上の「ページを開いている PC」。
- **ログイン**: 起動したら設定の ID でログインする。認証の失敗は 30 分ごと（`USER_NOT_FOUND` なら `--signup` を案内）、通信の失敗は 15 秒・30 秒・1 分・2 分・5 分の段で試し直す。ログインの情報はメモリだけに置く。
- **応答の環境**（`gas-client.mjs`）: 送る 1 回ごと（`createApi` の自動の再送を含む）に、失敗の応答も含めて応答の `env` を設定の env と比べ、違えばそれ以後は何も送らずに終了コード 2（ログの `env-mismatch`）。env を確かめられていない間（起動の直後・env のない失敗の応答の後）の書き込みは、先に `ownedWorlds` を読んで確かめてから送る（版 12 の GAS は失敗の応答に env を付けないので、失敗のたびに次の書き込みの前に 1 回読む。版 13 は認証の後の失敗にも env を付ける）。prod は `config.json` に `"env": "prod"` があるときだけ動く（引数や環境変数だけでは本番に送らない）。
- **送る本文の上限**: GAS の本文の上限（4 Mi 字＝4,194,304 字。`gas/Main.js`）を超える共有は送らず、ログに `upload-too-large`（10 分に 1 回）。テストのサーバー（1,770 体）で約 69 万字。上限は変えていない（2 万体ほどのワールドで超える。今の協力プレイも同じ）。
- **GAS の読み込みの増え方**: 共有を送るたびに、古い系統の判定のため `ownedWorlds` を 1 回読む（下の「古い系統の守り」）。ログインとワールドを読み始めたときに、共有の中身を 1 回読む。

### サブ PC への導入（ユーザーが行う）

**導入の条件**
- サーバーの PC はスリープしない設定にする（例: 管理者の PowerShell で `powercfg /change standby-timeout-ac 0`）。スリープの間はサーバーも常駐も止まる（P0 では PC が 1 時間スリープして、サーバーも計測も止まった）。
- ServerSync のアプリは起動したままにする（閉じていると、常駐は 30 秒ごとに PowerShell でプロセスを見て決める）。
- ServerSync のローカル API が 127.0.0.1 だけで待ち受けていること（`netstat -ano | findstr :54866` で `127.0.0.1:54866` だけ。P0 で確かめた）。
- REST のポート（8212）を外に出さない（ServerSync のトンネル〔インスタンスが開くポートすべてを出す〕・ルーターの転送をしない）。
  - 2026-10-19 にこの PC のテストのサーバーで見た結果: REST は `0.0.0.0:8212`（全部のアドレス）で待ち受ける（`netstat -ano | findstr :8212`）。さらに、PalServer の実行ファイルに、全部のポートを許す受信の規則（TCP・UDP。Public のプロファイルを含む）がすでにできていた（最初の起動のときの許可などで自動でできる）。そのため「ファイアウォールの許可をしない」だけでは足りず、REST は同じ LAN から届く（Basic 認証はある）。REST を切ることはできない（ServerSync の停止は REST の save → shutdown を使う。P0 の M9）。
  - そこで、管理者の PowerShell で、受信の TCP 8212 を止める規則を足す: `New-NetFirewallRule -DisplayName 'PalServer REST block' -Direction Inbound -Protocol TCP -LocalPort 8212 -Action Block`（止める規則は許す規則より優先する。同じ PC の中〔ループバック〕の通信はファイアウォールで止まらないので、ServerSync の save → shutdown は残る見込み）。ゲームの接続のポート（UDP）は止めない。
  - 足した後に確かめる: ServerSync の停止が今までどおり数秒で終わること・別の PC から 8212 に届かないこと（別の PC の PowerShell で `Test-NetConnection <サーバーの PC> -Port 8212` が `TcpTestSucceeded : False`）。規則を足すのはシステムの変更なので、PC の持ち主の了承を取ってから行う。
  - この PC（メインの PC）には 2026-10-19 に足した（`server` の決定 23）。テストのサーバーで、同じ PC の REST（127.0.0.1:8212）の save → shutdown は今までどおり通り（止まるまで 9 秒）、WSL から PC の LAN のアドレスの 8212 には届かなかった。
- 常駐は管理の操作（起動・停止・保存・REST）を持たない（ServerSync の状態の読み取りの GET だけ）。
- 本番のサブ PC の ServerSync は、ユーザー本人の Steam で動かす（変換で H が作成者の UID になるため）。サブ PC の時刻は日本時間（`Get-TimeZone`。保存の時刻で新旧を比べる前提）。
- タスクは Interactive なので、その Windows ユーザーでログオンしている間だけ動く（画面のロックはよい。ServerSync もログオン中のアプリ）。同じ Windows ユーザーに prod と test の両方は入れられない（`config.json` が env で分かれないため。`install.ps1` が止める）。
- 実機でまだ確かめていないこと（2026-10-19 時点。最初の導入で見る）: 管理者なしでログオン時のタスクを登録できること・ログオンで動き出すこと・窓の出方・`Stop-ScheduledTask` の後に子の node が残るか・サブ PC での DPAPI（Windows PowerShell 5.1 での復号。`-Mode Run`・`CheckOnline`）。`run-agent.ps1` の `-Mode Check` と 2 つのスクリプトの構文は、Windows のテストで 5.1 でも確かめている。

**手順**
1. 最新の協力プレイからインスタンスを作る（下の「往復」の「協力プレイ → サーバー」）。
2. ゲームの設定を合わせる（下の「ゲームの設定の合わせ込み」）。
3. 本番の `Users` に「サーバー」を作る（上の「共通パスワードと ID」。手順 7 の `-Mode Signup` で作ってもよい）。
4. Node 22 以上（24 LTS を勧める）と git を入れる: `winget install --id OpenJS.NodeJS.LTS -e`・`winget install --id Git.Git -e`。入れた後は、新しい PowerShell の窓で続ける（PATH を読み直すため）。
5. リポジトリを取る: `git clone <リポジトリの URL> <置き場所>`（`npm install` は要らない）。
6. 管理者ではない、いつもの PowerShell の窓で:
   - `cd <置き場所>`
   - `powershell -NoProfile -ExecutionPolicy Bypass -File tools\server-agent\install.ps1 -Env prod -UserId サーバー [-WorldName <名前>] [-Instance <インスタンス ID の頭>]`
   - node（22 以上）・git の確認 → `config.json`（prod なら `"env": "prod"`。前の項目は残し、引数で渡したものだけ書き換える）→ `--check`（通らなければ `config.json` を元に戻して止まる。サーバーのセーブがまだないときは `-SkipCheck`）→ 共通パスワードを 2 回（画面に出さず、DPAPI で暗号化して `passcode.dpapi` に保存）→ タスク スケジューラにタスク `PalNoteServerAgent-prod`（ログオン時・このユーザー・時間の上限なし）を登録、の順に進む。
   - `-WorldName` は共有に出すワールドの名前（なければ前の共有の名前）。`-Instance` は ServerSync のインスタンスが 2 つ以上あるときだけ要る（なければ `--check` が終了コード 2 で候補の頭 4 字を出す）。往復で作り直した後は古いインスタンスが残る（消さない限り 2 つになる）ので要る（下の「往復」の「協力プレイ → サーバー」の 5）。インスタンス ID とフォルダの組は `%LOCALAPPDATA%\ServerSync\instances.json` にある。
7. 常駐の ID がまだなければ作る: `powershell -NoProfile -ExecutionPolicy Bypass -File tools\server-agent\run-agent.ps1 -Env prod -Mode Signup`。
8. 確かめる: `run-agent.ps1 -Env prod -Mode Check`（GAS にはつながない。`--check`）→ `-Mode CheckOnline`（ログインと読み取りだけで、書かない。`--check --online`）。
9. 動かす: `Start-ScheduledTask -TaskName PalNoteServerAgent-prod`（次のログオンからは自動で動く。ログオンの直後に窓が一瞬だけ出る見込み。実機で未確認）。
10. サーバーを起動 → 参加して、画面で次を見る: 「ページを開いている PC」の「● サーバー（常駐） · … · サーバー稼働中」、共有した人が「サーバー」、所持パル・捕獲数・在庫・状態・ケーキ。
11. 常駐が最初の共有をした後（10 で共有した人が「サーバー」になってから）、画面でプレイヤーの対応を設定する（「以前のホスト（0000…0001）」の行を含む。決定 6・12）。この行はサーバーのセーブの共有で出る（協力プレイの共有では H はプレイヤーにいるので出ない。サーバーが止まっている間は常駐が読み込みも共有もしない）。設定の後、牧場のタマゴの自動登録を見る。

**見方**
- タスクの状態: `(Get-ScheduledTask -TaskName PalNoteServerAgent-prod).State`（Running・Ready）。
- ログ: `%LOCALAPPDATA%\pal-note-agent\prod\agent.log`（常駐）と `run-agent.log`（起動・終了コード・起動し直しだけ）。読み方は下の「ログの見方」。
- `run-agent.ps1` は、node の終了コードが 0・2・3 なら起動し直さず、ほかなら 30 秒後に起動し直す。
- `run-agent.ps1`（powershell.exe）そのものが落ちたときは、タスクに起動し直しの設定がないので、次のログオンまで動かない（タスクの状態が Ready のまま。`Start-ScheduledTask` で動かす）。

**更新**（画面と GAS を配信したら、サブ PC でもこの手順で更新する）
1. `Set-Content -LiteralPath "$env:LOCALAPPDATA\pal-note-agent\prod\stop.request" -Value stop`（常駐は 2 秒以内に気づき、送っている途中の共有を最大 15 秒待ってから state.json を書き出して終わる。終了コードは 0、state.json を保存できなければ 2）。
2. `(Get-ScheduledTask -TaskName PalNoteServerAgent-prod).State` が Ready になるのを待つ。
3. `git -C <置き場所> pull --ff-only`
4. `Start-ScheduledTask -TaskName PalNoteServerAgent-prod`
- 止めるときは `Stop-ScheduledTask` を使わない（子の node が残るおそれがある）。起動の後に `run-agent.log` が `exit code=3` なら古い node が残っているので、もう一度 `stop.request` を置いて止めてから動かす。

**止め方・消し方**
- 止める: 上の `stop.request` を置く（次のログオンまで動かない）。`run-agent.ps1` が起動し直しを待つ 30 秒の間に置いても止まる。動いていない間に置いた `stop.request` は、次の起動のときに消す（その起動を止めない）。
- 自動で動かさない: `Disable-ScheduledTask -TaskName PalNoteServerAgent-prod`（戻すときは `Enable-ScheduledTask`）。
- 消す: `stop.request` で止める → `Unregister-ScheduledTask -TaskName PalNoteServerAgent-prod -Confirm:$false` → `%LOCALAPPDATA%\pal-note-agent\prod\` を消す（`passcode.dpapi`・`state.json`・ログ）。ほかの env がなければ `config.json` も消す。`state.json` には古い系統の守りの状態と牧場の記録が入っているので、消すと次は「記録だけ」から、守りも判定待ちから始まる。

**DPAPI**
- `passcode.dpapi` は、その PC のその Windows ユーザーでしか戻せない（ファイルを写しても使えない）。常駐を入れる PC・ユーザーごとに `install.ps1` を実行する。Windows のパスワードを管理者がリセットした（本人が変えたのではない）ときも戻せなくなることがある。そのときは `install.ps1` をやり直す（`run-agent.log` に「passcode.dpapi を戻せません」）。
- `run-agent.ps1` は戻したパスワードを子の node の環境変数 `PAL_AGENT_PASSCODE` にだけ渡す（自分の環境変数・ユーザーの環境変数・ファイル・ログには置かない）。node は読んだらすぐ環境変数から消す（その後に起動する PowerShell などに受け継がせない）。動いている間は `run-agent.ps1` のメモリに .NET の文字列として残る（消せない）。

### 引数と終了コード

`node tools/server-agent/main.mjs [引数]`（`npm run agent`。`npm run agent:check` は `--check`）。設定の優先順位は 引数 ＞ 環境変数 ＞ `config.json`。

| 引数 | 環境変数・`config.json` の項目 | 意味 |
|---|---|---|
| `--env test\|prod` | `PAL_AGENT_ENV`・`env` | 既定は test。prod は `config.json` に `"env": "prod"` があるときだけ |
| `--user <ID>` | `PAL_AGENT_USER_ID`・`userId` | 常駐の ID（「サーバー」） |
| `--world <フォルダ>`（`--world-dir` と同じ） | `PAL_AGENT_WORLD_DIR`・`worldDir` | ワールドのフォルダ（`…\SaveGames\0\<ワールド ID>`） |
| `--server-root <フォルダ>` | `PAL_AGENT_SERVER_ROOT`・`serverRoot` | サーバーのフォルダ（`GameUserSettings.ini` の `DedicatedServerName` でワールドを決める） |
| `--instance <ID の頭>` | `PAL_AGENT_INSTANCE`・`instance` | ServerSync のインスタンス（2 つ以上あるとき） |
| `--world-name <名前>` | `PAL_AGENT_WORLD_NAME`・`worldName` | 共有に出すワールドの名前（64 字まで） |
| `--auto-register`・`--no-auto-register` | `PAL_AGENT_AUTO_REGISTER`・`autoRegister` | 配合牧場の自動登録（既定はオン） |
| `--verbose` | — | debug のログも出す |

- パスワードは環境変数 `PAL_AGENT_PASSCODE` だけ（test のときは `.env.local` の `PAL_TEST_PASSCODE` も読む）。`config.json` に秘密は書かない（上の 7 項目だけを読み、知らない項目は使わずにログで知らせる）。接続先は `PAL_API_URL`（既定は本番の URL。https だけ。`localhost`・`127.0.0.1`・`[::1]` なら http も受ける）、データの場所は `PAL_AGENT_DATA_DIR`。
- ワールドの見つけ方は、設定の `worldDir` → 設定の `serverRoot` → `%LOCALAPPDATA%\ServerSync\instances.json` の各インスタンス（`<インスタンス>\bin\Pal\Saved\Config\WindowsServer\GameUserSettings.ini` の `DedicatedServerName` がワールド ID）。設定したパスで見つからなければ、自動の発見に進まずに終了コード 2。複数のインスタンスが候補なら、更新日時で選ばずに `instance` を求める。`instance.json`・`PalWorldSettings.ini`（パスワードを含む）は読まない。
- 動かし方（どれか 1 つ）:
  - なし: 常駐として動く（タスク）。
  - `--check`: GAS にはつながず、見つけたワールドの解析の要約（体数・プレイヤー数・プレイ中の人数・牧場・タマゴ・日数・clock と保存時刻の有無）・サーバーの状態・古い系統の守りの状態を出す。名前・ワールド ID・インスタンス ID は出さない（見つけ方と場所のドライブだけ）。ServerSync のローカル API への状態の GET と、PowerShell のプロセスの一覧は使う。
  - `--check --online`: ログインと `ownedWorlds` の読み取りだけ（書かない。presence も送らない）。公開されている同じワールドの共有の時刻・体数・日数・種類と、送ったのがこの常駐かを出す。
  - `--dry-run --once`: 送る中身を組み立てるが送らない（書き込み〔共有・登録・presence・対応〕は記録だけ。読み取りは送る）。サーバーが止まっていても今のセーブを読む。要約には人の名前・ID と配合表の子を出さない。
  - `--once`: 1 回だけ読んで送り、presence を 1 回送って終わる（サーバーが動いていなければ読まない）。`--once --force-host` は test 環境だけで、止まっているサーバーのセーブも読んで送る。ログイン・稼働の確認・ワールドの登録・読み込み・共有・自動登録・presence を 1 つの期限（120 秒）で切る。
  - `--accept-world`: 古い系統の受け入れ（下の「古い系統の守り」）。動いている常駐があれば `accept.request` で伝える。
  - `--signup`: 常駐の ID を作る（先に読み取りで応答の環境を確かめてから作る。すでにあれば 0）。
  - `--online` は `--check` と、`--dry-run`・`--force-host` は `--once` と一緒にだけ使える。
- `--check`・`--check --online`・`--dry-run --once`・`--signup` は state.json・ログのファイル・二重起動の防止を書かない（標準出力だけ）。

| 終了コード | 意味 | `run-agent.ps1` |
|---|---|---|
| 0 | 正常に止まった（`stop.request`・シグナル）・送れた | 起動し直さない |
| 1 | 想定外（通信の失敗を含む）。`--once` では、セーブを読めない・通信の失敗・判定待ち・期限切れ（`once-timeout`）・presence の失敗 | 30 秒後に起動し直す |
| 2 | 設定や環境の誤り（再起動しても直らない）: 設定・引数・ワールドが見つからない・応答の env の違い・state.json を保存できない。`--once`・`--accept-world`・`--signup`・`--check --online` では認証の失敗（`USER_NOT_FOUND`・パスワードの誤りの `AUTH`）も 2（常駐として動くときは 30 分ごとに試し直し、終わらない）。`--once` では止めた状態・上限超え・形の誤りなども | 起動し直さない（直してから `Start-ScheduledTask`） |
| 3 | 二重起動（この環境の常駐がすでに動いている） | 起動し直さない |

`%LOCALAPPDATA%\pal-note-agent\`（`PAL_AGENT_DATA_DIR` で変えられる。`install.ps1` は決めた場所をタスクの引数 `-DataDir` に入れ、`run-agent.ps1` が子の node に渡す。場所を変えたら `install.ps1` をやり直す）。

### ログの見方

1 行は `<時刻（UTC）> [info|warn|error|debug] <出来事> 項目=値 …`（debug は `--verbose` のときだけ）。ID・パス・IP は伏せて書く（GUID と 32 桁の 16 進は頭 8 字＋…、Steam ID は `7656…`、インスタンス ID は頭 4 字＋…、インスタンスのフォルダは `<instance>`、ユーザーのフォルダは `%USERPROFILE%`、IP は `<ip>`、パスワードは `<secret>`）。プレイヤー名・パスワード・GAS の応答の中身は書かない（数と結果の種類だけ）。

| 出来事 | 意味 |
|---|---|
| `started`・`logged-in`・`world` | 起動・ログイン（env）・見つけたワールド（見つけ方とドライブ） |
| `world-not-found` | ワールドが見つからない（理由と、インスタンスが 2 つ以上なら候補の頭 4 字）。終了コード 2 |
| `already-running` | この環境の常駐がすでに動いている。終了コード 3 |
| `config-error`・`config-warning` | 設定・引数の誤り（終了コード 2）・設定の知らせ（`config.json` の知らない項目など。動きは続ける） |
| `unexpected`・`tick-failed`・`loop-failed` | 想定外の例外。`unexpected` は終了コード 1（`run-agent.ps1` が 30 秒後に起動し直す）。`tick-failed`・`loop-failed` は 10 秒ごとの確認・定期の処理の 1 回の失敗で、常駐は動き続ける（続くなら `--verbose` で見る） |
| `server-state` | サーバーの状態が変わった（`running`・`grace`・`stopped`・`unknown` と見つけ方 `source`）。`reasons` はそう決めた・決められなかった理由: `serversync:unreachable`〔ServerSync に届かない。実行ファイルのパスで決める〕・`serversync:not-here`〔ServerSync は動いていると言うが、この PC では対象の PalServer が動いていない。止まっているとして扱う（猶予の後 `stopped`）。別の PC が共有のインスタンスを動かしているか、フォルダのパスが実行ファイルのパスと合わない〔ジャンクションなど〕〕・`serversync:unconfirmed`〔この PC で動いているかを確かめられない。`unknown`〕・`process-error` など |
| `attached`・`attach-waiting` | 読み始めた・`Level.sav`・`LevelMeta.sav` がまだない |
| `detaching`・`detached lastUpload=…` | 止まった後の最後の送信の結果（`sent`・`timeout`・`none`・`skipped`〔送れる状態でなかった。ログインしていないなど〕・`error:<code>`・`unconfirmed`〔unknown で送らなかった〕） |
| `files-added` | `Players` に増えたファイルを足した |
| `upload` | 共有の結果（`status`・`result`・`error`。種類が変わったときだけ info・warn。同じ結果の繰り返しは debug） |
| `upload-too-large` | 本文の上限を超えたので共有しない（10 分に 1 回） |
| `read-failed` | セーブを読めない |
| `login-failed`・`logged-out` | ログインの失敗（試し直すまでの時間）・認証が外れた（30 分後にログインし直す） |
| `env-mismatch` | 応答の環境が設定と違う。何も書かずに終了コード 2（原因を直してからタスクを起動する） |

| `auto-register`・`auto-register-notices` | 自動登録のトーストの文・通知の件名ごとの数 |
| `kv-error`・`kv-unsaved` | state.json を書けない（`kv-unsaved` は終わるときに書けなかった。終了コード 2。データのフォルダに書けるか・ウイルス対策を確かめる） |
| `stop-requested`・`stopped code=…` | `stop.request` を見た・止まった |
| `once-skipped`・`once-failed`・`once-timeout` | `--once` の結果 |

### 古い系統の守り（ユーザーの決定 18）

協力プレイで進めた後に取り込み直していない古いサーバーのワールドを起動しても、新しい共有を古い中身で上書きしないための守り（`tools/server-agent/lineage-guard.mjs`）。サーバーの保存時刻はいつも「今」なので、GAS の新旧の比べ方（保存時刻）では防げない。

- **比べ方**: ワールドが動いた通算の時間（`clock`。`Level.sav` の `RealDateTimeTicks`）が両方にあれば `clock` どうし、どちらかになければゲーム内の日数どうし、日数もどちらかになければ比べない（送ってよい）。ティックと日数を混ぜたり、大きい方を取ったりはしない。
- **比べる相手**: (a) GAS で公開されている同じワールドの値（受け入れたことがあれば、受け入れの基準より後に公開された世代だけ）、(b) この常駐が前に送った値。どちらかより小さければ「古い系統」として止める。
- **判定待ち**: 起動したとき・セーブを読んだたびに、そのセーブはまず判定待ち。公開の値を読み、古い系統でないと確かめたら、そのセーブ（保存時刻）に限って解除する。読んでいる間・読めない間（通信の失敗）も判定待ち（ログの `lineage-pending`。共有のエラー「公開されている共有と照らせていないため、共有と自動登録を待っています」。読めるようになれば 30 秒ごとに判定し直して送る）。解除は、判定したときの動いている間（attach）の中だけ効き、次に動いたときは同じセーブも照らし直す。
- **判定待ち・止めている間に止めるもの**: 共有、自動登録の候補の取り込み、登録の直前の送信（`createAutoRegister` の `paused`。画面のページは `paused` を渡さないので、画面の動きは変わらない）。
- **止めた状態は state.json に残す**（ログの `lineage-blocked`。理由 `published`〔公開の値〕か `sent`〔前に送った値〕と、比べた値）。明示の受け入れまで、再起動しても、遊び続けて値が公開の値を追い越しても解除しない。共有のエラーは「古い系統のセーブのため、共有と自動登録を止めています（受け入れるときは --accept-world）」。
- **受け入れ**（`--accept-world`。タスクで動かしているなら `run-agent.ps1 -Env prod -Mode AcceptWorld`）:
  - そのときのセーブの値と、受け入れたときに GAS から読んだ公開の世代の `uploadedAt`（GAS のサーバーの時計）を受け入れの基準として残し、(b) も受け入れたセーブの値にする。PC の時計は使わないので、PC の時計がずれていても効く。受け入れた後に別の PC が公開した新しい系統では、また止まる。
  - 動いている常駐には `accept.request` で伝える（2 秒以内に受け入れ、結果は常駐のログの `accepted`・`accept-failed`。要求は書いてから 10 分で無効）。動いている常駐は、今動いている間に読んだセーブの値を基準にする（ディスクの次の保存を基準にすると、受け入れの直後にまた止まるため）。まだ読んでいない・止まっているときは今の `Level.sav` を読む。止まっている間に受け入れたときは、次に動いたときの読み込みで送る。
  - 二重起動の防止を持っているのが `--once` のときも、`--accept-world` は「伝えました」と出して 0 で終わるが、`--once` は `accept.request` を読まない（要求は 10 分の間残り、その間に起動した常駐が受け入れる。過ぎたら捨てる〔`accept-expired`〕）。`--once` が終わってから、残った `<env>\accept.request` を消して `--accept-world` をやり直し（残すと、後で起動した常駐がもう一度受け入れ、候補と牧場の記録をまた捨てる）、ログの `accepted`（常駐がないときは `accept-done`）を確かめる。
  - 公開の世代がない・読めないときは受け入れない（読めないときは 30 秒ごとに試し直す）。
  - 受け入れると、止めていた間の候補と牧場の記録を捨て、最初の読み込みと同じく「記録だけ」から始める（その時点で牧場にあったタマゴは登録しない）。
  - **受け入れる前に、本当に新しい系統かを確かめる**: 画面の最後の共有の日数（「ゲーム内 N 日目」）・時刻と、常駐の `--check` の日数を照らす。古いワールドを受け入れると、新しい共有をその古い中身で上書きする。
- **state.json が壊れていたとき**: 空から始めると止めた状態・受け入れの基準・前に送った値を失うので、写しを `state.json.broken-<日時>` に残し、見つけたワールドを止めた状態にする（ログの `lineage-unreadable`）。公開されている共有と照らしてから `--accept-world` で戻す。値の形が違う状態も、止めた状態として扱う。
- **公開の行がないのに止まったとき**（共有を削除した後に (b) で止まったなど）は、公開の世代がないので受け入れられない。そのときは常駐を止めて `<env>\state.json` を消す（守りの状態と牧場の記録も消え、次は判定待ち・「記録だけ」から始まる）。
- **限界**（手順で守る）:
  - 古いワールドを初めて読む PC（その常駐が前に送った値を持たない）で、そのワールドの値がすでに公開の値を追い越していれば見分けられない（同じ通算の時間なので、系統そのものは区別できない）。
  - 協力プレイの側（古いコピーをホストした場合）には守りがない。
  - 守ること: 古いインスタンスは起動しない（協力プレイから戻すときは作り直す）。別の PC で建てる前に、最後の共有とセーブの日数・時刻を照らす（下の「別の PC への引き継ぎ」）。

### 往復（協力プレイ ⇄ サーバー）（ユーザーの決定 5）

**協力プレイ → サーバー**
1. 協力プレイの最後のホストの PC で、このページが最後の保存を共有し終えたのを確かめる（ヘッダーのセーブ連携の「共有」）。ゲームを終えて SaveSync の同期を通す。以後、そのワールドを協力プレイでホストしない。
2. 協力プレイのフォルダ一式を、バックアップのドライブ（リポジトリ・`SaveGames` の下・インスタンスの中は避ける）に写す。
3. サブ PC に最新の協力プレイのワールドを用意する（写す元は、ユーザーが H〔最後のホスト〕の PC）。ServerSync でインスタンスを**作り直す**（前の古いインスタンスは起動しない）。作った後に確かめる:
   - `npm run check:save -- "<インスタンス>\bin\Pal\Saved\SaveGames\0\<ワールド ID>"` で、日数（「ゲーム内: N 日目」）とプレイヤーが、協力プレイの最後のセーブ（同じく `npm run check:save`）と同じ（ワールド ID も協力プレイと同じ。体数はグローバルパルボックスの分だけ少ない。サーバーにはないため）。
   - `Players` に `00000000000000000000000000000001.sav` がなく、作った人の UID のファイルがある。ほかの人のファイル名は協力プレイと同じ。
4. ゲームの設定を合わせる（下の「ゲームの設定の合わせ込み」）。
5. 常駐を新しいインスタンスに向けて動かしてから、サーバーを起動する（常駐が最初の共有者になる）。常駐は起動したときにワールドを 1 回だけ探すので、動いたままの常駐は古いインスタンスを見続ける（古いインスタンスは動かないので読まず、新しいサーバーの共有も自動登録もしない）。常駐を入れてあれば（2 回目から）、次の順で向け直す:
   1. `stop.request` で常駐を止める（上の「サブ PC への導入」の「更新」の 1・2）。
   2. 古いインスタンスを残すなら（インスタンスが 2 つあると、常駐は終了コード 2 で止まる）、`install.ps1 -Env prod -UserId サーバー -Instance <新しいインスタンス ID の頭>` で設定を新しいインスタンスにする（ID は `%LOCALAPPDATA%\ServerSync\instances.json` で新しいフォルダと照らす。共通パスワードをもう一度入れる）。前に `-Instance` を入れていたら、古いインスタンスを消しても必ず入れ直す（`install.ps1` は前の項目を残すので、渡さなければ古いインスタンスに結び付いたまま）。`config.json` に `worldDir`・`serverRoot` を書いていたら、新しいインスタンスのパスに直す。
   3. `run-agent.ps1 -Env prod -Mode Check` で、`world`（見つけ方）・`check-save`（日数）・`check-server` を見る。
   4. `Start-ScheduledTask -TaskName PalNoteServerAgent-prod` で動かす。
   - 取り込んだ直後のセーブは保存の時刻が協力プレイの最後と同じなので `same`・`unchanged`（書かない）になり、サーバーが保存した後のセーブから `newer` で載る（変換で保存の時刻〔`Level.sav` の `Timestamp`〕が保たれる前提。実機で未確認）。
6. 仲間の画面: 登録はそのままでよい（参加と判定され、常駐の共有を見る。同じワールド ID の行）。プレイヤーの対応は `i:` の鍵なのでそのまま効く。必要なら「以前のホスト」の行を選ぶ。

**サーバー → 協力プレイ**（変換はユーザーが行う）
1. ServerSync でサーバーを停止する（ServerSync は REST の save → shutdown → 自動バックアップ。P0 の M9）。常駐が最後の保存を共有し終えたのを、画面の「最後の共有」で確かめる（停止から最大で約 2 分。猶予の 60 秒と最後の送信の 60 秒）。
2. 変換する PC はユーザーの PC（U を H に戻すのがユーザーの UID なので、協力プレイの `Players\savesync.sav`〔SaveSync が書く、H の枠の人の本当の UID〕と合う）。変換の前に協力プレイのフォルダを写す。
3. 変換は作業用のフォルダで行い、確かめてから協力プレイのフォルダに置く:
   - `SaveGames` の下に途中のものを置かない（Steam Auto-Cloud と SaveSync が拾う）。
   - 協力プレイの `WorldOption.sav` を残す（サーバーのセーブにはない。なくなると協力プレイの設定が既定に戻る）。
   - `LocalData.sav` は協力プレイのフォルダのもの（サーバーで遊んだ間に書かれた新しいもの）を残す。
   - `Players` のファイル名が U から H（`00000000000000000000000000000001.sav`）に戻ることを確かめる。
4. 変換した PC（ユーザー）が最初にホストする。このページをその PC で開いておく（登録はそのまま。ファイルを置き換えただけなら許可も残る。読めなければ登録し直す）。最初の共有は保存の時刻がサーバーの最後と同じなので `same`（書かない）、自動登録の証拠も `same` で捨てる（サーバーの常駐が担当した分）。次の保存から `newer` で載る（変換で保存の時刻〔`Level.sav` の `Timestamp`〕が保たれる前提。実機で未確認）。対応と「このワールドでの自分」は `i:` の鍵なので、同じキャラクターに付いたまま。
5. ゲームを終えて SaveSync の同期を通すまで、ほかの人はホストしない。
6. 古いサーバーのインスタンスはもう起動しない（ServerSync で停止のままにする。消すかはユーザー）。もう一度サーバーにするときは、上の手順で最新の協力プレイから作り直す（常駐を新しいインスタンスに向け直すのは上の 5）。協力プレイの間、サーバーの PC の常駐は止めなくてよい（サーバーが止まっている間は読まない。「ページを開いている PC」に「サーバー停止中」の行が出たままになる）。

**注意**
- 同時に両方で進めない（両方が保存すると、同じワールド ID の共有が新しい時刻の方へ交互に入れ替わり、自動登録も二重に試みる）。
- 古いサーバーを後から起動しない（中身が古くても保存の時刻は「今」なので、GAS の新旧の比べ方では防げない。常駐の古い系統の守りが止めるが、上の限界がある）。
- 全員が日本時間であること（サブ PC も同じ）。
- 協力プレイのホストの交代（SaveSync）は今までどおり。サーバーの期間は SaveSync を使わない。サーバーで遊んだ後にゲームを終えても、SaveSync は協力プレイのフォルダを書き換えなかった（P0 の M8）。

### 別の PC への引き継ぎ（ユーザーの決定 14）

仲間も ServerSync の共有で同じサーバーを建てるかもしれない。常駐はどの PC にも入れられる（PC ごとに `install.ps1`。DPAPI は PC・ユーザーごと）。同時に動かすのは 1 台。どちらの手順も、**前後で全プレイヤーの InstanceId と最後の共有を照らしてから遊ぶ**:
- 最後の共有: 画面の「ゲーム内 N 日目」と最後の共有の時刻が、前の PC の最後より進んでいるか（新しい PC の常駐の `--check` の日数でも見られる）。
- InstanceId: 新しい PC の常駐が共有した後、設定の「プレイヤーの対応」で全員が前と同じ ID に対応づいたままか（対応は InstanceId の鍵なので、同じなら外れない。「未設定」の行が増えたら、そのキャラクターの InstanceId が変わっている）。

**ServerSync の共有で、同じサーバーを別の PC（B）が建てる**
1. 前の PC（A）でサーバーを停止し、A の常駐が最後の保存を共有し終えたのを画面で確かめる。
2. B で ServerSync の受け取りが終わったのを確かめる（ServerSync の画面）。動いているインスタンスがどの PC のものかも確かめる（常駐は、ServerSync が動いていると言っても、その PC で対象のフォルダの PalServer が動いていなければ読まない。ログの `serversync:not-here`）。
3. B の常駐の `--check`（`run-agent.ps1 -Env prod -Mode Check`）で、体数・日数と `check-lineage blocked=false` を見てから、B でサーバーを起動する。
4. 受け取りが終わる前の古い写しで動かすと、B の常駐の古い系統の守りが止める（ログの `lineage-blocked`）。そのときは受け取りを終え、セーブが最後の共有に追いついたのを確かめてから `--accept-world`。

**協力プレイから変換し直す**（別の人がサーバーを建てる）
1. 変換（ServerSync のインスタンスの作成）は、H を作成者の UID に置き換える。変換する人の Steam で H がだれの UID になるかを確かめる: 協力プレイの `Players\savesync.sav`（H の枠の人の本当の UID）が、変換する人のと合うこと（最後にホストした人が変換する）。合わないと、H のキャラクターが変換した人の UID に付け替わり、その人の元のキャラクターと取り違えるおそれがある（実機では確かめていない）。
2. 残りは上の「協力プレイ → サーバー」と同じ（作り直す・設定を合わせる・常駐を新しいインスタンスに向けて動かしてから起動）。前の PC のサーバーは起動しない。

### ServerSync のローカル API で使ってよい操作

ServerSync のローカル API（`http://127.0.0.1:54866`）は**認証がない**（同じ PC のプロセスなら、どれでも起動・停止・削除を呼べる）。使う操作を決めて守る:
- 使ってよい: 状態の読み取り（`GET /instances/<インスタンス ID>` など）・起動と停止（`POST /instances/<インスタンス ID>/action` の `start`・`stop`）・手動のバックアップ（`POST /instances/<インスタンス ID>/backup`）。
- `revert`（設定とセーブをバックアップの時点に戻す）は、ユーザーの了承の後だけ。
- 上にない操作（インスタンスの削除・全消し〔`POST /instances/purge`・`DELETE /account`〕・ファイルの書き込みなど）は使わない。
- 常駐が使うのは状態の `GET` だけ。応答には起動の計画（管理者パスワードを含みうる）が入るので、画面やログに貼らない。
- 起動の後、誰かが接続するまで `status.state` は `Starting` のまま（`status.running` は起動から true）。停止は ServerSync が REST の save → shutdown をして数秒で止まる（P0 の M9・M10）。
- ただし、誰も接続していない間（`Starting`）は、`stop` が 409（`AlreadyRunning`。「まだ起動中です。オンラインになってから停止してください」）で断られる（2026-10-19 に確認）。誰かが一度接続すれば止められる。誰も接続せずに止めるときは、同じ PC から REST の save → shutdown を呼ぶ（Basic 認証。ユーザー名は `admin`、パスワードは ini の `AdminPassword`。画面やログに出さない）: `POST http://127.0.0.1:8212/v1/api/save` → `POST http://127.0.0.1:8212/v1/api/shutdown`（本文 `{"waittime":1,"message":"stop"}`）。ServerSync の状態は `Stopped` になる（起動し直されない）。

### ゲームの設定の合わせ込み（scripts/server-settings.mjs）

ServerSync はインスタンスを作るときに協力プレイの `WorldOption.sav` を持ち込まないので、サーバーは ini（`<インスタンス>\bin\Pal\Saved\Config\WindowsServer\PalWorldSettings.ini` の `OptionSettings`）の値で動く（P0 の前は 18 項目違った。孵化の時間 72 時間 ← 1 時間、デスペナルティ「全部」← 「アイテム」など）。決定 11・19 で協力プレイに合わせる。
- 差の表（読み取りだけ）: `node scripts/server-settings.mjs --coop "<協力プレイのワールドのフォルダ>" --instance "<インスタンスのフォルダ>"`（`--ini "<PalWorldSettings.ini>"` で直接指定してもよい）。分類は「合わせる候補」「要確認」（`bAutoResetGuildNoOnlinePlayers`）「サーバーだけの値」（ServerName・ポート・REST など）「ini にない（既定で動く）」「WorldOption.sav にない」。パスワードの項目は読まない・比べない・書かない・出さない。ServerName・ServerDescription・PublicIP は伏せて出す。
- 書き換え: `--apply game`（合わせる候補を全部）か `--apply <キー,キー>`。PalServer が動いていないとき（`tasklist` で確かめる）だけ、ini の `OptionSettings` の中の対象の `Key=Value` だけを協力プレイの値に書き換える（ほかは 1 バイトも変えない。ini にないキーは足さない）。数は今の値の桁で書く（`1.000000` なら 6 桁）が、その桁で書くと値が変わるとき（整数で書かれた項目に 1.5 など）は丸めず、サーバーの float の形（`1.500000`）で書く。書く前に読み直して、書く項目が協力プレイの値にならなければ、写しも書き込みもせずに止める。書く前に同じフォルダに `PalWorldSettings.ini.before-<日時>` を残す。ServerSync は止まっている間の手での編集を取り込む。サーバーは止めるときに ini を書き直すが、値は残った（P0 の M5）。動いている間に手で直した値は、止めるときに上書きされる見込み。
- 確かめ方: 起動の後、REST の `/v1/api/settings`（Basic 認証。応答にパスワードの項目はない）で値が効いているか。
- P0 で決めたこと: 合わせる候補の 9 項目を協力プレイに合わせた。`bAutoResetGuildNoOnlinePlayers` は false のまま（公式の説明では、ギルドのメンバーが誰もログインしないと拠点と建物を消す。遊ぶときだけ動かすサーバーでは、間を空けて再開すると消えうる）。最大人数は ServerSync の設定（maxPlayers）で変える（起動の引数でも渡るため）。
- 本番のサブ PC: インスタンスを作った後に同じ道具で同じ差を出し、同じ内容で書く（ini はインスタンスごと）。
